# Working on Home Hub

A private family web app (static site on GitHub Pages + Supabase). See `README.md` for what it does and `docs/v2-design.md` for the v2 build contract.

## Before every PR

- Run `tests/run.sh` and make sure it ends with `0 failed` and exit status 0 (about 16 minutes). It runs, in order:
  - the database tests (`tests/db/run.sh`): RLS, functions, recurrence in a throwaway Postgres;
  - the contract check (`tests/contract/check.sh`): every `.rpc()` / `.from()` in the site and the Edge Functions names a function or table that exists in the migrated schema, with argument names it takes, and that the caller (signed out, signed in, Edge Function) may use. Rename a function or a parameter and this fails until every caller is updated;
  - the Edge Function tests (`tests/fn/*.test.ts`);
  - the browser tests (`tests/e2e/*.test.js`), against a JavaScript fake of Supabase (`tests/e2e/mock.js`);
  - the real-database tests (`tests/realdb/run.sh`): the same pages in Chromium against the real schema, migrations, RLS and functions, so the fakes can't drift unnoticed (about 3 minutes);
  - the docs check (`tests/docs/*.test.js`): this file, `README.md` and `docs/v2-design.md` against the code (deploy secrets, test suites, function signatures, tables and columns), and the function signatures in `docs/v1.1-google-calendar.md`, `docs/v1.2-kitchen.md`, `docs/v1.3-homework.md` and `docs/v1.4-project-guests.md`; and (`labels.test.js`) that no file carries a word of a medical or learning label.
  `tests/run.sh fn e2e` runs only the suites named. See `tests/README.md`.
- New behaviour gets new tests. Never weaken or delete an existing check to make a change pass; fix the code, or explain in the PR why the old expectation was wrong.

## Database changes

- `supabase/schema.sql` is the v1 baseline. Don't edit it for new work.
- Every schema change is a new, numbered file in `supabase/migrations/` (`0002_home_hub_v2.sql`, `0003_google_calendar.sql`, `0004_meals_and_shopping.sql`, `0005_homework.sql`, `0006_homework_school.sql`, `0007_homework_coach.sql`, `0008_school_check.sql`, `0009_school_keys.sql`, `0010_hearth_people.sql`, `0011_project_guests.sql`, `0012_coach_rewards.sql`, `0013_recipes.sql`, `0014_day_language.sql`, `0015_school_assigned_dates.sql`, `0016_school_redate_keeps.sql`, `0017_bring_tomorrow.sql`, `0018_school_given_keep.sql`, `0019_routine.sql`, `0020_family_board.sql`, `0021_coach.sql`, `0022_watch_list.sql`, `0023_school_marks.sql`, `0024_project_selections.sql`, `0025_weekly_sheets.sql`, `0026_homework_counts.sql`, `0027_task_calendar.sql`, then `0028_…`). A fresh install is `schema.sql` followed by `migrations/*.sql` in order.
- `supabase/preflight.sql` is for 0002 only (a v1 database before v2). 0003, 0004, 0005, 0006, 0007, 0008, 0009, 0010, 0011, 0012, 0013, 0014, 0015, 0016, 0017, 0018, 0019, 0020, 0021, 0022, 0023, 0024, 0025, 0026 and 0027 check for themselves: each refuses to run without the one before it, or twice, and any clash rolls it back.
- Migrations are additive, so the site that is already live keeps working until it is updated, and each runs in one transaction.
- Follow the rules in `docs/v2-design.md` §3: RLS on every table, `set search_path = ''` on every function, and explicit `revoke … from public, anon` / `grant … to authenticated` on every new public function.
- Keep `docs/v2-design.md` in step: a new or changed table, column or public function, or a changed signature, goes in it in the same PR (the docs check names what's missing).

## Deploy order (needs Supabase access; from `docs/v2-design.md` §7)

0. Move the project into the paid organization (owner); confirm the URL and project ref are unchanged.
1. Run `supabase/preflight.sql` (read-only checks) and `list_migrations`.
2. Merge the client PRs. The site stays in v1 mode until step 3 (the core reads `hub_schema_version()`; when it's missing, the site shows the v1 pages).
3. Apply the migration (the site switches to v2 on next load).
4. Deploy `hub-jobs` from main with verify_jwt false (`supabase/config.toml` pins it for the CLI; with the dashboard or the Supabase MCP's `deploy_edge_function`, whose default is true, turn it off by hand). Secrets: `HUB_CRON_SECRET` (at least 32 characters); `SITE_URL` (required: the site's address, for the links in the emails; without it every run stops with `stop: 'config'` and Settings → Preview answers 503); `RESEND_API_KEY` and `EMAIL_FROM` (required) and `EMAIL_FROM_NAME`, the same as for `send-email`; `HEALTHCHECK_URL`, which is optional; and for Google Calendar (v1.1) `GOOGLE_SA_JSON`, also optional: the whole service-account key file (without it the calendar job stops with `not_set_up` and the morning email is unchanged); and for v1.3's AI planner `ANTHROPIC_API_KEY`, also optional: the key from the family's Anthropic workspace (without it the `homework_ai` action answers `not_set_up` and everything else works; README → Homework → The AI planner); and for v2's calendar inbox `RESEND_WEBHOOK_SECRET` and `INBOX_ADDRESS`, also optional: the Resend receiving webhook's signing secret and the hub's email address with its random part, and `INBOX_ALSO_FROM`, a member's second sending address (`other@…=member@…`) (without the first two the webhook answers 503 `not_set_up` or ignores the mail; `docs/v2-design.md` §28).
5. Create the two Vault secrets by hand (`hub_cron_secret`, the same value as `HUB_CRON_SECRET`, and `hub_jobs_url`, the function's address), then run `supabase/cron.sql`. Its header has the exact commands; it refuses to run while either is missing or a placeholder. Run it again after every release that changes it (v1.1 adds the `hub-calendar` job, and v1.3's school feed, migration 0006, the `hub-school` job); it is safe to run again.
6. Smoke checks: no header → 401; preview → rendered JSON; Settings shows the last run; next morning `notification_log` has sent rows.
7. Ops hardening: Auth email rate limit about 6/hour; the signup hook stays on; Resend click/open tracking off.

## Test data

Never put real names, phone numbers, email addresses, street addresses, account numbers, Supabase project refs or other real IDs in fixtures, tests, screenshots or examples. Use made-up people (Alex, Sam, Jordan, Taylor, Morgan, Pat Lee), fictional numbers in the 555-0100 to 555-0199 range (for example `(201) 555-0100`), and `example.com` or `.example` addresses. Never give anyone, real or made up, a medical or learning label: not in a column, a word list, a prompt, a fixture, a screenshot or a doc (`docs/v1.3-homework.md` §13.1 item 8). The list of such words lives only in `tests/docs/labels.test.js`, which checks every file.

## Client code

- `assets/hub.js` is the core: sign-in, the shell and router, forms, data access, message helpers, toasts. Pages are modules in `assets/modules/`. Each one calls `HomeHub.register({ name, schema: { min, max }, nav, match, render })`; the contract is documented at the top of the "MODULES & SCHEMA VERSION" section of `hub.js`.
- A module is shown only when the database's schema version (from `hub_schema_version()`, or 1 when that function doesn't exist or the request gets no answer at all) is within its `schema` range.
- `index.html` loads `config.js`, supabase-js, `gantt.js`, `hub.js`, `shoplist.js` (the shopping list's shared pieces, also used by My day), `plan.js` (v1.3: homework's shared pieces, the plan editor, the week strip, the timelines (Next 3 weeks, an assignment's chart, his path) and the timer's arithmetic, also used by My day and the tutor link; no database calls of its own), then the module files (the v1 pages, the v2 pages, `food.js`, from 0022 `watch.js`, and `homework.js` last), in that order, without `async`. A new module needs its own script tag after `hub.js`.
- Every script and stylesheet in `index.html`, `day.html` and `board.html` carries the same `?v=…` (for example `?v=20261025a`). Bump all of them together, in all three files, to one new value, in every release that changes any of those files, so phones don't mix old and new code. (The docs check fails while they differ.)
- `share.html` is the public project page. It uses `gantt.js` and `styles.css` but not the hub, so check it still works when you change those (the e2e tests cover it).
- `day.html` is the second public page, with no sign-in, in three modes: **My day**, for kids and helpers (`day.html?t=<day token>`); the confirmation email's question (`day.html?c=<confirmation secret>#confirm`, which shows only the confirm question); and from v1.3 the **tutor link** (`day.html?h=<tutor link>`, with no `t=`), which loads nobody's day and shows one kid's homework in `plan.js`'s tutor view. It loads `config.js`, supabase-js, `assets/shoplist.js`, `assets/plan.js` and `assets/day.js`, in that order, not the hub, and shares `styles.css` (plus `assets/css/day.css` and `assets/css/plan.css`), so a change to `styles.css` or `plan.js` needs checking there too (`tests/e2e/day.test.js`, `tests/e2e/tutor.test.js` and the realdb tests cover it). It calls only the twenty-eight anon token functions (`get_person_day`, `complete_by_token`, `undo_by_token`, `confirm_digest`, `stop_digest`, from 0014 for My day's English | Español `set_language_by_token`, from 0019 for his routine's ticks `routine_tick_by_token`, from 0022 for a kid's movies and shows `watch_by_token` and `watch_add_by_token`, from 0026 for his count's +1 and −1 `count_by_token`, and for the helper's shopping list `get_list_by_token`, `add_to_list_by_token`, `buy_item_by_token`; from v1.3, for a kid's homework `homework_by_token`, `step_by_token`, `plan_by_token`, `focus_by_token`, `reward_by_token`, `assignment_by_token`, `homework_prefs_by_token`, and from 0006 his New from school's `school_item_by_token` (from 0015 with `p_due` for an item dated the day it was assigned), and in the tutor link's mode only `tutor_view_by_token`, `tutor_assignment_by_token`, `tutor_plan_by_token`, `tutor_step_by_token`, and from 0007, for a link whose coach view a parent turned on, `coach_view_by_token` and `coach_note_by_token`, and from 0012, for a link whose coach view and Can manage rewards are both on, `coach_reward_by_token`), plus, in the tutor link's mode only, `functions.invoke('hub-jobs')` for v1.3's AI planner (its `homework_ai` action, with the link's token in the body).
- `board.html` is the third public page (from 0020, `docs/v2-design.md` §25): the **family board**, `board.html?b=<board link>`, one screen for the whole house with no sign-in. It loads `config.js`, supabase-js and `assets/board.js`, in that order, not the hub, with `styles.css` and `assets/css/board.css`. It calls only the board's four token functions (`board_by_token`, `board_tick_by_token`, `board_undo_by_token` and `board_routine_by_token`), never a My day one, and shows what the wall may show: private items read "Private item", and there are no notes, phone numbers, homework, points or shopping list (`tests/e2e/board.test.js` and the realdb tests cover it).

## Secrets

`config.js` holds only the publishable key. Never commit a `service_role` or secret key, an access token, or a Resend API key.
