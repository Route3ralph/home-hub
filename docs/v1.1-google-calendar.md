# Home Hub v1.1 — Google Calendar and Hearth (design)

This is the build contract for v1.1, the part `docs/v2-design.md` §0 deferred. It is written against v2 as it is live: migration `0002_home_hub_v2.sql`, the `hub-jobs` Edge Function and `supabase/cron.sql`. Every table, column and function named here either exists there or is added by migration `0003_google_calendar.sql` (§2). It was revised after four reviews; §10 lists what changed and what was turned down, and what the review of the build changed.

Research facts H1…H9 and G1…G9 come from the same research brief as v2. The ones this design rests on:
- Hearth shows Google calendars only. It has no API (H1). Its Google events are view-only (H2). It puts a whole calendar in one person's column; single events can't be moved to another column (H3).
- Hearth gives no alerts for synced events (H7). Home Hub's morning email stays the reliable channel.
- A service account can't add attendees (G1). Reminders set through the API only reach the account that set them (G5).
- The Calendar API is free: 600 requests a minute per user, and a service account counts as one user (G6).
- Event ids we choose may use only the characters `[a-v0-9]`, must be 5 to 1024 characters long, and must be unique within a calendar (G8).
- Checked for this revision on Google's pages: the OAuth scope `calendar.events.owned` ("See, create, change, and delete events on Google calendars you own"); `events.list` takes `eventTypes=default` ("Regular events"; unset returns every type) and answers with the caller's `accessRole` and the calendar's `summary`.

What the owner asked for: "a shared calendar … Gmail calendar … Integration with Hearth display would be ideal". The family wants it plain, low-maintenance and reliable. Two rules follow from that:
- **Home Hub's database is the source of truth.** Google gets a one-way copy of hub items.
- **Google is also read.** Events people type into Google (or onto the Hearth wall, if those reach Google, §5.5) are read back and shown in the hub. They are never changed there.

Examples use the test household from `tests/realdb/seed_v2.sql`:
- Alex and Morgan are the parents (admins).
- Sam is an adult.
- Jordan is a kid.
- Taylor is the helper, and speaks Spanish.

## 0. Decisions on one page

- **One PR, built on the service account.** Gate 1 (the key downloads) is checked before the build is merged; gate 2 (the service account can write to a shared calendar) is the first **Test** in Settings after the deploy (§1.2). The OAuth fallback is specified in full (§1.4, §6.2) but built only if a gate fails. Nothing else changes between the two: only how the access token is obtained.
- **One Google calendar per Hearth column.** The family creates them by hand in the family Gmail (a service account can't create calendars in someone else's account): one per person who should have a column, plus Family. Pets and House are optional. Admins paste each calendar's ID into **Settings → Google Calendar & Hearth**, one calendar at a time.
- **Nothing is copied until an admin has looked at it.** After a calendar is set up, Settings shows everything that would go on it (the job's whole window, yesterday to 60 days ahead), with **Make private** on each row, and copies only after **Start copying**.
- **A reconciler, not a queue.**
  - SQL works out the Google events the hub *should* have, for a rolling window (yesterday to 60 days ahead), from the same rules `agenda(p_from, p_to)` uses, so repeats, one-day changes, daylight saving and `private.current_due(t)` stay in one place.
  - Each event has an id that is always the same for the same item on the same Google calendar, and a hash of its content.
  - `hub-jobs` compares that list with `calendar_links` (what it last wrote) and calls Google only for the differences. A burst of edits becomes one update, and a lost reply sorts itself out on the next run.
- **Two new actions in `hub-jobs`, not a new function.** `calendar` runs every 5 minutes from pg_cron and is also the admins' **Sync now**. `calendar_test` is for admins. The Google code lives in new files `google.ts`, `calendar.ts` and `util.ts`.
- **Which calendar an event goes on decides whose it is. Attendees are never used.**
  - The person in charge gets the event, and everyone along gets a copy. Events with 4 or more family members go once on Family.
  - Unassigned items go on Family (or Pets and House, if those are set up).
  - Done tasks and cancelled days are deleted. Late tasks become one "2 late: …" line per column on today.
  - Health tasks and private items show only as "Private item".
- **The wall is public.** Everyone in the house sees it: the family, the helper, guests and the renovation crew. Copied: titles, times, the place, and a linked directory entry's name and number. Never copied: notes, day notes, the family's own phone numbers or emails, account numbers, My day or confirmation links.
- **Changes made in Google to the hub's events are put back**, and the parents are told: each event's description starts with "Made by Home Hub: changes made here are undone", Settings lists what was put back, and the next morning email says so.
- **Events read from Google** come back as kind `'google'` from a new `google_items(p_from, p_to)`. `agenda` doesn't change, so nothing read from Google can be written back. They show on Today and Calendar for everyone who signs in. A kid's or helper's My day gets those of a calendar that is that person's (writing, or read-only and given to them), and Pets or House if they own it; a kid also gets Hub – Family's and those of a read-only Family calendar marked "Show to kids"; a helper never gets a Family calendar's.
- **Schema version 3.** Migration 0003 makes `hub_schema_version()` return 3. The new client shows the Google card, and asks for Google events, only on version 3, so it can go live before the migration.
- **Owner's time:** about 2–2½ hours over three sittings (§1.3).

### 1.2 The two gates, and the fallback

- **Gate 1: the service-account key downloads.**
  - This is setup step A (§1.3), with no code involved. The owner does it before the PR is merged.
  - Keys can be blocked in Google Cloud organizations made since May 2024 (G4). So the project is made in a parent's own personal Gmail, under **No organization**.
  - If Google says "Service account key creation is disabled", gate 1 has failed. The PR is then built on OAuth instead (§1.4, §6.2).
- **Gate 2: the service account can add, delete and restore an event on a calendar shared with it.**
  - The first **Test** in Settings is this gate (step D, on Taylor's calendar). What Test does is in §6.5.
  - Gate 2 has failed if, after the calendar is shared with **Make changes and see event details**, Taylor's Test still says "Home Hub can't change this calendar", "Shared correctly, but Google won't let Home Hub add an event to it" (Google listed the calendar with the writer role, then refused the insert), "Google refused to use this calendar", or "Google answered differently than expected". A small follow-up PR then adds the OAuth token (§6.2) and its docs; the database, the reconciler and the pages stay as they are.
  - A Test that names "Make changes (see private events as free/busy)" (access role `writerWithoutPrivateAccess`) is not gate 2 failing: the wrong sharing option was chosen. Share it again with **Make changes and see event details**.
- **The OAuth fallback** uses the family Gmail's own sign-in, with the app published **In production**: an app left in Testing gets refresh tokens that expire after 7 days (G2). Personal-use apps under 100 users need no verification, only a click-through warning (G3).

## 2. Database: migration `0003_google_calendar.sql`

Fresh install = `schema.sql`, then `0002`, then `0003`. Like 0002, it runs as one transaction and is additive, and every rule in v2-design §3 applies:
- RLS on every table.
- `set search_path = ''` on every function.
- `revoke execute … from public, anon` on every new function, public and private (functions are executable by PUBLIC by default), then a grant to whoever calls it.
- Audit columns come from `private.stamp()`. Every job timestamp uses `private.now()`, so the tests can move the clock.
- No new SECURITY DEFINER function: the job functions run as `service_role`, and the rest with the caller's rights.

The migration opens with a guard. It first checks `to_regprocedure('public.hub_schema_version()')`, so a v1 database gets the friendly message "Home Hub v2 (migration 0002) isn't installed" rather than "function does not exist"; then it raises "Google Calendar (migration 0003) is already installed" unless `hub_schema_version()` returns 2. It ends by making `hub_schema_version()` return 3; `create or replace` keeps the function's grants. Any clash with an existing name rolls the whole transaction back, so no preflight file is needed (`preflight.sql` stays a 0002-only check).

### Tables
```

  -- for_kids, and update those and copy_approved_at; nothing else)
  id uuid PK default gen_random_uuid()
  google_id text not null unique         -- Google's "Calendar ID"; trimmed and lowercased by trigger
    check (google_id ~ '^[a-z0-9._+#-]{1,200}@[a-z0-9.-]+\.[a-z]{2,}$')   -- '#' for holiday calendars (read only)
  kind text not null check in ('person','pets','house','family')   -- whose column it is
  person_id uuid → people on delete cascade                        -- kind 'person' only
  label text not null (trimmed, 1–40 characters)   -- what Settings calls it: the person's first name, "Family",
                                                   -- or for pets and house the title prefix ("Dogs: Heartworm pill")
  writes boolean not null default true   -- the hub copies its items here; false = only read
  for_kids boolean not null default false   -- read-only Family calendars: "Show to kids" (§5.4)
  copy_approved_at timestamptz           -- "Start copying" after the preview; null = nothing is inserted or updated
  -- written by hub-jobs only
  google_name text                       -- the calendar's name in Google (events.list "summary"), from the last read or Test
  access_role text                       -- events.list "accessRole" from the last read or Test
  status text not null default 'new' check in ('new','ok','no_access','error')
  status_detail text                     -- one line, at most 300 characters: a fixed message and Google's reason
  checked_at timestamptz                 -- the last time Google answered about it (read, write or Test)
  read_at timestamptz                    -- the last complete read of its events
  created_at, updated_at, updated_by
  checks: (kind = 'person') = (person_id is not null);
          not writes or google_id ~ '^[a-z0-9._-]+@group\.calendar\.google\.com$'   -- never a main (personal) calendar
          not for_kids or (kind = 'family' and not writes)
  unique index calendars_one_writer on (kind, coalesce(person_id, '00000000-0000-0000-0000-000000000000')) where writes
  triggers (BEFORE INSERT OR UPDATE; same-event triggers fire in name order, so stamp runs before tidy):
    calendars_stamp (private.stamp());
    calendars_tidy (private.calendars_tidy()): trims label, lowercases google_id; a changed google_id resets
      status to 'new' and clears google_name, access_role, checked_at, read_at and copy_approved_at (the old
      calendar's cached events stop showing at once, because pages match google_events.google_calendar to the
      row's google_id, and the next run deletes them: the trigger runs with the admin's rights, which can't
      write google_events); an update that changes only hub-jobs' columns keeps the old updated_at
      (so the job's status writes every 15 minutes don't look like an admin's edit).
  RLS: members select; admins insert, update, delete.

  google_calendar text not null          -- the Google calendar it was written to, as in the plan row (never re-derived)
  base_id text not null check (base_id ~ '^hh[0-9a-f]{32}$')     -- private.calendar_event_id(p_key), §3.2
  event_id text not null check (event_id ~ '^hh[0-9a-f]{32}$')   -- the id in Google: base_id, or a new one after a clash

  calendar_id uuid → calendars on delete set null   -- null: the mapping is gone, so the event is deleted
  item_kind text check in ('event','task','project','late'), item_id uuid, job_id text, occurrence date
  part text not null default '' check in ('','start','finish')   -- a long project job's two markers
  day date not null, end_day date not null   -- the first and last household day the Google event covers, as last written
  title text not null default ''         -- as written, for Settings
  hash text                              -- md5 of the body last written; null = write it again
  tried_hash text                        -- the hash (or 'delete') of the last attempt, for the backoff rule (§3.3)
  google_hash text                       -- the content hash of Google's copy after our last write (§5.2)
  google_updated timestamptz             -- Google's "updated" after our last write
  repairs int not null default 0, repaired_at timestamptz,
  repair_kind text check in ('edited','deleted')   -- put back after a change in Google (§5.2)
  status text not null default 'pending' check in ('pending','ok','error')
  attempts int not null default 0, next_try_at timestamptz, failing_since timestamptz, error text

  event_id text not null                 -- Google's id (for one day of a repeating Google event, the instance's id)
  title text not null                    -- cleaned "summary", one line, at most 200 characters; '' when it has none

  location text                          -- cleaned, one line, at most 200 characters; null for a private one
  all_day boolean not null
  start_day date not null, end_day date not null   -- the household's days, inclusive

  repeating boolean not null default false
  google_updated timestamptz, read_at timestamptz not null
```

Grants: `revoke all … from anon` on all four tables. On `calendar_links`, `google_events` and `calendar_sync`, `authenticated` keeps only `select` (Supabase's default privileges would also give it insert, update, delete, truncate, references and trigger; truncate ignores RLS). On `calendars`, `authenticated` keeps `select` and `delete`, plus the column-level `insert` and `update` above.

### Functions

Pages (`authenticated`, `service_role`):
- `google_items(p_from date, p_to date) returns setof public.agenda_item`. STABLE, SECURITY INVOKER, so members see the rows and everyone else sees none. Like `agenda`, it raises unless the range is 1 to 62 days. The mapping is in §5.3.
- `calendar_preview(p_calendar uuid) returns table (day date, title text, private boolean, item_kind text, item_id uuid, place text, details text)`. STABLE, SECURITY INVOKER; raises unless `private.is_admin()`. Everything **Start copying** puts on that calendar: `private.calendar_desired` for the job's window (`today_local() − 1` to `today_local() + 60`, the same days as the plan), as the wall will show it. `place` is the event's place as copied; `details` the rest of the description the wall shows (who's on it, a directory entry's name and number), on one line, or null.

Job functions (`service_role` only; revoked from `authenticated`):
- `calendar_begin() returns jsonb` → `{go, stop, run_id}`. Takes the lease in one `update … where running_since is null or running_since < private.now() − 10 minutes returning`, so two callers can't both get `go`. `stop` is `'busy'` or `'paused'` (`paused_until` is in the future) when `go` is false.
- `calendar_signed_in(p_run uuid, p_auth text, p_account text, p_key_id text) returns void` records how this run signed in, once Google has given it a token.
- `calendar_read_due(p_force boolean default false, p_limit int default 10) returns table (calendar_id uuid, google_id text, writes boolean, w_from date, w_to date, time_min timestamptz, time_max timestamptz, tz text)`. STABLE. Lists the calendars to read now:
  - never-read ones first (`read_at is null`), then the one Google answered about longest ago (`greatest(read_at, checked_at)`), so a calendar whose reads are always cut off (an old `read_at`, a fresh `checked_at`) doesn't go first every run;
  - those with `read_at` older than 14 minutes; `no_access` and `error` ones at most once an hour, so fixed sharing is noticed by itself;
  - with `p_force` (an admin's **Sync now**), every mapped calendar.
  - `time_min` is local midnight at the start of the window, and `time_max` local midnight after its last day, both in the household zone.
- `calendar_store_events(p_calendar uuid, p_google_id text, p_from date, p_to date, p_name text, p_access text, p_complete boolean, p_events jsonb, p_seen jsonb) returns jsonb` stores one calendar's read in one transaction and returns its counts (§5.2). It does nothing if the row is gone or its `google_id` is no longer `p_google_id`.
- `calendar_mark(p_calendar uuid, p_google_id text, p_status text, p_detail text default null, p_name text default null, p_access text default null) returns void` records what a failed read, a write's 403 or a Test found about one calendar, again only while its `google_id` is `p_google_id`. `no_access` also deletes that calendar's `google_events`.
- `calendar_plan(p_site text default null, p_limit int default 60) returns table (op text, calendar_id uuid, google_calendar text, base_id text, event_id text, gen int, item_kind text, item_id uuid, job_id text, occurrence date, part text, day date, end_day date, title text, body jsonb, hash text, pending int, hiding int)`. STABLE and read-only: it gives the next Google writes (§3.3) and changes nothing.
- `calendar_record(p_results jsonb) returns void` records what Google answered for a batch of those writes. Each result is handled in its own sub-block, so one bad row doesn't lose the others.
- `calendar_finish(p_run uuid, p_result jsonb, p_stop text default null, p_error text default null) returns void` ends a run (§3.4). It releases the lease only while `run_id` is still `p_run`; its clean-up (old cached events, failed writes that have gone past) runs whatever the run id.

Every function not marked STABLE above is VOLATILE. All clean-up happens in `calendar_finish`.

Private:
- `private.calendar_event_id(p_key text) returns text` — IMMUTABLE: `'hh' || md5(p_key)`. That is 34 characters from `[0-9a-h]`, inside base32hex (G8).
- `private.calendar_desired(p_from date, p_to date, p_site text)` — STABLE: the events Google should have (§3.2). Granted to `authenticated` (for `calendar_preview`; `private` isn't exposed through the API) and `service_role`.
- `private.calendar_word(p_key text, p_lang text) returns text` — IMMUTABLE: the new words (`finishes`, `made_by_hub`, `skip_hint`, `open_in_hub`, `who_is_on`, `pets`, `house`, `calendar_warning`, `calendar_items_failed`, `calendar_put_back`, `edited_in_google`, `deleted_in_google`), falling back to `private.word(p_key, p_lang)`.
- `private.clean_text(p_text text, p_max int) returns text` — IMMUTABLE: removes control characters, line and paragraph separators, bidi overrides and isolates (U+202A–202E, U+2066–2069) and zero-width characters, folds spaces, and cuts to `p_max` characters. The pattern is written in SQL (`\uXXXX` escapes), never in the Edge Function's source.
- `private.google_for(p_person uuid, p_from date, p_to date, p_grown_up boolean) returns setof public.agenda_item` — STABLE: the Google rows that reach this person's day (§5.4).
- `private.calendars_tidy()` — the trigger above.

## 3. Sync: the reconciler

### 3.1 The window, and the past
- `w_from = today_local() − 1`, `w_to = today_local() + 60`. That is 61 days apart, inside `agenda`'s limit.
- Yesterday is included so that a late-night edit, or a run just after midnight, still reaches yesterday's events.
- **The past is kept.** A link that is no longer desired and whose `end_day` is before `w_from` is history: it stays in Google, so phones keep the past. Two exceptions, whatever the day:
  - its item has been deleted, or is now private (or a health task) → the event is deleted;
  - a late-tasks line (`item_kind 'late'`) is never kept.
- **Link rows are kept**, not forgotten after 30 days, so these exceptions and Disconnect reach the past too. That is about 2,000 rows a year.
- Multi-day items count by their last day: a trip that started before `w_from` and is deleted while it is still going is taken off Google.
- Events further ahead than 60 days reach Google as the window reaches them. The Calendar page says so past `calendar_sync.window_to`, and before `window_from` (§5.4).

### 3.2 Desired events: `private.calendar_desired(p_from, p_to, p_site)`
- **Input.**
  - Events and tasks from `agenda(p_from, p_to)` (run as service_role, or as an admin for the preview, so it sees everything): events whose status isn't `cancelled`; tasks with status `open` and `occurrence >= today_local()`.
  - Project jobs straight from `projects.task_dates`, with `agenda`'s filters: projects that are `on_calendar`, whose status isn't `idea`, `on-hold` or `done`, with `task_dates` not null, jobs whose status isn't `done`, dates read with `private.safe_date(s)`, overlapping the window, and the trade's directory entry found the way `agenda` finds it. `agenda`'s project rows can't be used: they carry the project's id and the job's start day, so two jobs of one project starting on the same day (the fixture's "Wire" and "Inspection") would get one id. Only the first row per (project, job id) is used; `gantt.js` already refuses two jobs with one id.
  - From `late_items()`: every late task, for the late-tasks lines (§4, rule 8).
  - Each row goes through `private.active_only(a)`, so people who are off the family list count as nobody; `participant_ids` are de-duplicated.
  - Never `google_events`: no Google event is ever copied back to Google.
- **Routing** follows §4. Its result is one row per (item, occurrence or job, Google calendar, part).
- **Key and id.** `base_id = private.calendar_event_id(p_key)`, where `p_key` is:
  - events and tasks: `<kind>|<item id>|<occurrence>|<Google calendar ID>|`, the occurrence written `to_char(occurrence, 'YYYY-MM-DD')` (not `date::text`, which follows the session's DateStyle). A task's occurrence is its due date as `current_due` gives it;
  - project jobs: `project|<project id>|<task_dates[].id>|<Google calendar ID>|<part>`, so a job that is renamed or moved keeps its id and is updated;
  - late-tasks lines: `late|<Google calendar ID>`, so the line keeps its id from day to day.
  - The key holds the Google calendar ID, not the row's uuid: re-pointing a row deletes the old events and inserts new ones anyway, and this way the same item never meets its own old id on a different calendar.
  - The id in Google is `base_id`, or `'hh' || md5(p_key || '|' || gen)` once a clash has bumped `gen` (§3.5).
  - If two desired rows still share a (Google calendar, `base_id`), only the first in a fixed order is kept, and the db tests assert that the fixture never has any.
- **Body** (jsonb, built in SQL; Taylor's Piano on Tue Nov 3, the first Tuesday after the clock change: Taylor is in charge and Jordan is along):
  ```json
  { "id": "hh0c5e…",
    "status": "confirmed",
    "summary": "Piano (con Jordan)",
    "location": "Rivera Music, 12 Elm St",
    "description": "Hecho por Home Hub: si lo cambias aquí, se deshace. Se cambia en Home Hub.\nRivera Music 555-0150",
    "start": { "dateTime": "2026-11-03T21:00:00Z", "timeZone": "America/New_York" },
    "end":   { "dateTime": "2026-11-03T22:00:00Z", "timeZone": "America/New_York" },
    "transparency": "opaque", "visibility": "default",
    "extendedProperties": { "private": { "homehub": "1", "homehub_base": "hh0c5e…", "homehub_kind": "event",
                                         "homehub_item": "<events.id>", "homehub_occurrence": "2026-11-03" } } }
  ```
  - Timed items carry the instants `agenda` computed, written with `to_char(x at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"Z"')` (never `to_jsonb(timestamptz)`, which prints in the session's TimeZone), plus the household's `timeZone`. Google never has to resolve a local time, so the hour that happens twice on Nov 1 can't go wrong.
  - All-day items have `start.date` and `end.date`, where `end.date` is the day after `end_day` (Google's end is exclusive).
  - A task with a time is a 30-minute event.
  - All-day events are `transparent` (they don't block free/busy) and timed ones `opaque`.
  - There are no `attendees` (G1), no `reminders` (G5: each person's calendar defaults apply) and no `colorId`.
  - `status: "confirmed"` is always sent, so an update brings back an event someone deleted in Google (Test checks this, §6.5).
  - Project jobs add `homehub_job` and `homehub_part` to `extendedProperties.private`; a late-tasks line has `homehub_kind: "late"` and no item.
  - Fixed words use the language of the person the calendar belongs to, or English for Pets, House and Family.
- **Hash:** `md5(body::text)`. A jsonb value prints the same way every time, and nothing in the body depends on session settings, so the SQL editor, PostgREST and the tests get the same hash.
- `p_site` is the site's address as `render.ts` `siteBase()` normalises it; hub-jobs passes `siteBase(SITE_URL)`.

### 3.3 Plan and record
`calendar_plan(p_site, p_limit)` compares `calendar_desired(w_from, w_to, p_site)` with `calendar_links`, matched on (Google calendar, `base_id`).

| Case | Op |
|---|---|
| Desired, no link, or a link never written successfully (`synced_at` null) | `insert` (with the link's `event_id` if it has one) |
| Desired, link's `hash` is null or differs | `update` |
| Link not desired, `end_day >= w_from` | `delete` |
| Link not desired, `end_day < w_from`, item deleted or now private or a health task, or a late-tasks line | `delete` |
| Link not desired, `end_day < w_from`, otherwise | nothing: the past is kept |
| Link whose `calendar_id` is null, whose `google_calendar` isn't its row's Google ID any more, or whose row no longer `writes` | `delete`, whatever its day: disconnecting a calendar takes the hub's events off it |
| Link of a project that is `on_calendar` and under way but whose `task_dates` is null (stale) | nothing, neither delete nor update. Settings says "<project>'s dates are out of date: open it in Projects" |

- **Skipped:**
  - inserts and updates for a calendar whose `status` isn't `ok`, whose `access_role` isn't the one this sign-in needs (`writer` for the service account, `owner` for OAuth), or whose `copy_approved_at` is null. A calendar is `ok` only after a read or Test at its current Google ID (§5.2), so a just-pasted ID is never written to before the hub has looked at it;
  - deletes on a calendar whose status is `no_access` or `error`, except deletes for gone mappings (above), which are tried like any other op;
  - a link with `next_try_at` in the future, **unless** the desired hash differs from `tried_hash`: a fix in the hub is tried at once;
  - everything while `calendar_sync.paused_until` is in the future.
- **Hiding never waits for a calendar in `error` that the hub can still write to.** A calendar renamed in Google (the name rule), shared with "Make changes and manage sharing" (`owner`), or refused by one read (403, 400, 409) is `error`, yet Google still lets the hub change its own events there. So on a calendar whose status is `error` and whose last-seen `access_role` is `writer` or `owner`, an update whose new body has `visibility: private` (an item made private) and a delete go ahead for a link written there (`synced_at` set); inserts and other updates still wait. On a `reader` calendar in `error`, and on any `no_access` one, everything waits: the hub can't write there. (An update that makes an item private also goes ahead on an `ok` calendar the hub can write to whatever its approval.)
- **No op ever targets a calendar with `writes` false**, except deleting links the hub itself recorded there (a row switched from writing to read-only).
- **Order**, fully fixed:
  1. updates whose new body has `visibility: private` and a hash that differs (an item just made private);
  2. deletes that hide something now: of a link whose `end_day` is in the window (gone mappings included), or of an item that is now private or a health task, wherever its day;
  3. everything else, by `day`, then `title`, then `base_id`, so today and tomorrow reach the wall first;
  4. the other deletes of the past (a deleted item's history, old late lines and project markers, a disconnected calendar's history), so that Disconnect, `remove_person` or deleting a long series never holds up today's changes for many runs.
- At most `p_limit` rows come back. Each row also carries `pending`, the total still to do, and `hiding`, how many of those are deletes or updates that make an item private (groups 1, 2 and 4), so Settings can say "Copying 214 items to Google…" or "Hiding 3 items in Google…". hub-jobs counts down the same ops as it does them.

`calendar_record(p_results)` takes an array of the plan rows, each with `ok`, `gone`, `clash`, `forget`, `google_hash`, `google_updated`, `http` and `error` added. For every row, `calendar_id` is `(select id from calendars where id = r.calendar_id)` (null if the row was disconnected during the run, so the next plan deletes the event as a gone mapping), and `google_calendar` is taken from the plan row as it is.
- **Insert or update done:** the link is upserted with status `ok`, `hash`, `tried_hash`, `day`, `end_day`, `title`, `google_hash` and `google_updated`, with `synced_at` now, and `attempts`, `failing_since`, `error` and `next_try_at` cleared.
- **Delete done, or the event already gone:** the link row is deleted.
- **Clash** (§3.5): `gen + 1`, the new `event_id`, `synced_at` and `hash` null. The next plan inserts with the new id.
- **Failure:**
  - the link is upserted with status `error`, `attempts + 1`, `tried_hash`, `failing_since` (if not already set) and the error (one line, at most 300 characters);
  - `next_try_at = now + 5 min × 2^(attempts − 1)`, at most 6 hours;
  - a failed delete also sets `hash` to null, so if the item becomes desired again it is written again (and the link leaves `error`);
  - a failed insert leaves `synced_at` null, so the next plan tries the insert again; if Google did make the event, the insert's 409 turns into an update (§3.5).
- **Gone past** (settled in `calendar_finish`, §3.4): a failed insert or update (never a delete: `tried_hash` isn't `'delete'`) whose item is no longer wanted and whose `end_day` is before the window, on a calendar still mapped (the row exists at that Google ID and writes). Like any past event, Google's copy stays as history: a link never written (`synced_at` null) is forgotten, any other is `ok` again, with `attempts`, `next_try_at`, `failing_since` and `error` cleared. Without this, a write that failed until its day passed (a 400, a long 5xx streak, a calendar `no_access` for a day or two) would stay in Settings' problems and in every parent email for good. A failed delete is tried until it works (privacy), and a link whose item is still wanted (moved ahead) stays, to be tried again.
- **Forgotten** (the link row is deleted): a gone-mapping delete that has failed 10 times, or one that met a confirmed calendar-level 403 or 404 (`forget`). Until then Settings' problem list shows it.

### 3.4 One run of `hub-jobs` `{action: 'calendar'}`
1. **Who.** Either the header `x-hub-cron` matches `HUB_CRON_SECRET` (pg_cron, compared in constant time as `digest` does), or a signed-in admin (`whoami()` role `admin`): that is **Sync now**, which also forces reads. Anyone else gets 401 or 403.
2. **`calendar_begin()`.** Without migration 0003 (PostgREST answers that the function doesn't exist), the answer is 503 `{stop: 'no_schema'}`. `busy` or `paused` → 200 with that `stop`, and nothing else happens.
3. **Config.**
   - `GOOGLE_SA_JSON` unset → `calendar_finish(…, 'not_set_up')` and 200 `{stop: 'not_set_up'}`. Google is never called.
   - A secret that is there but unusable gives `stop: 'config'` with a fixed message, never the parser's error text (V8's JSON errors quote the input, so a mis-pasted key would leak into `last_error`, which members can read).
4. **Token.** If Google refuses the key: `calendar_finish(…, 'auth')`, 500. Otherwise `calendar_signed_in(p_run, …)`.
5. **Read** (§5.1), at most 20 seconds: for each row of `calendar_read_due(p_force, p_limit)` (with `p_force` for Sync now), list its events and call `calendar_store_events(…)`. No read call starts after 20 seconds (or with less than a second left), each read call's timeout is cut to the time left, and a read call that times out isn't tried again. So a calendar whose list call hangs costs one timeout, never the writes: they always get the rest of the run, privacy first. Running out of read time ends the reads, not the run.
6. **Write:** `calendar_plan(siteBase(SITE_URL), 60)`, then each op in turn (§3.5).
   - The results go to `calendar_record(p_results)` in batches of 20, so a run that dies loses at most 20 results. Those heal on the next run, because the ids don't change.
7. **Stops:**
   - a rate-limit answer (`slow_down`);
   - a 403 that is about the whole setup (`config`, §3.5);
   - 30 seconds since the run started (`time`): no new Google call starts after that, so a run plus its last call's 15-second timeout ends inside pg_net's 60 seconds, and the rest goes in the next run. The budget is checked before every op (and the reads' 20 seconds before every page).
8. **`calendar_finish(p_run, p_result, p_stop, p_error)`.**
   - Releases the lease (only for this run), and sets `last_run_at`, `last_result`, `last_stop`, `last_error`, `window_from` and `window_to`.
   - Sets `last_ok_at` when the run had no run-level stop (`not_set_up`, `config`, `auth`, `error` or `slow_down`). `time` is not a failure, and neither are single items that failed (§5.6), except a run that ran out of time without writing anything while writes were pending (`pending` > 0): that one leaves `last_ok_at`, so runs that keep getting nowhere show in the parents' email after 2 hours.
   - On `not_set_up`, `config` and `auth`, clears `auth`, `account` and `key_id`, so Settings never says "Signed in as…" while signing in fails.
   - Starts or extends the pause on `slow_down`; a run that wrote successfully sets `pause_step` back to 0.
   - Deletes the `google_events` rows no read has refreshed for 24 hours (each store stamps `read_at` on the rows it keeps, and a cut-off read keeps the days it covered), so a calendar that keeps failing doesn't show week-old events while a calendar whose reads are always cut off keeps what it read; and rows read from a Google ID the calendar no longer has.
   - Settles failed writes that have gone past (§3.3).
   - Answers 200 with the counts, or 500 for `auth`, `config` and `error`. That way pg_net's log shows the failures, as it does for `digest`.

The request body is ignored except for `action` (and, for `calendar_test`, a uuid `calendar_id` that must name an existing `calendars` row). No recipient, calendar ID or content is ever taken from it.

### 3.5 Google calls and their answers

Calls go to `https://www.googleapis.com/calendar/v3/calendars/{google_calendar}/events[/{event_id}]`, with both ids put through `encodeURIComponent`, and `sendUpdates=none` on writes. Each call has a 15-second timeout (a read's is cut to what is left of the reads' 20 seconds, §3.4), and calls are at least 250 ms apart. Write answers are not trimmed with `fields`: the content hash and `updated` come from them. The helper that makes these calls is named `gcal(…)`, not `call(…)`: the contract check reads any `call('<string>', …)` as a database function.

"The calendar is reachable" below means a read or write on it succeeded in this run, or it was `ok` and checked in the last 10 minutes. Otherwise a 404 or 410 is checked with a **probe**, `GET …/events?maxResults=1&fields=accessRole`: a 200 means the event is gone; a 403 or 404 means the calendar can't be reached (`no_access`, and the link stays in `error` with its backoff). The probe also answers with the hub's access role there, which decides what one event's 403 means (below). It is made at most once per calendar and run.

A **leftover** is a delete whose mapping is gone (§3.3: Disconnect, a new Google ID, a calendar switched to read-only). A refusal there says nothing about a calendar the hub uses, so it is never marked (`calendar_mark`), and the calendar's other leftovers are still tried: each is forgotten (`forget`) in the same run when the calendar can't be reached or written.

| Op | Call | Answer → what happens |
|---|---|---|
| insert | `POST …/events` with the body (with `id`) | 200 → ok. **409** (the id exists: written before, or deleted in Google, which keeps deleted ids) → `PUT …/events/{id}`; if that PUT gets 404 or 410, or a 403 that doesn't stop the run (`forbiddenForNonOrganizer`, `forbidden`, `requiredAccessLevel`, any other), the id is taken by an event the hub can't write on this calendar (someone moved it to another calendar in Google, which leaves a cancelled copy behind that belongs to the other calendar; the POST's 409 already says the hub may write here): **clash**, and the next run inserts with a new id (`gen + 1`). |
| update | `PUT …/events/{id}` | 200 → ok. **403 `forbiddenForNonOrganizer`** (the event was moved to another calendar in Google) → **clash**. **404 or 410** on a reachable calendar → `POST`, then as insert. At most 3 calls per op. |
| delete | `DELETE …/events/{id}` | 204 → ok. **404 or 410** on a reachable calendar (or after the probe) → `gone`. |
| any | | **429**, or 403 with reason `rateLimitExceeded`, `userRateLimitExceeded`, `quotaExceeded` or `dailyLimitExceeded` → stop, `slow_down`.<br>**403** with reason `accessNotConfigured` or `SERVICE_DISABLED` (step A.2 was skipped) → stop, `config`: "The Google Calendar API isn't turned on in the Cloud project (README, step A.2)". `insufficientPermissions` or `ACCESS_TOKEN_SCOPE_INSUFFICIENT` → stop, `config`: "Google's sign-in for Home Hub doesn't include the calendar scope".<br>**403** `requiredAccessLevel` or `forbidden` on one event → the probe: if it can't reach the calendar, or the hub's access role there isn't `writer` or `owner`, → `no_access` for that calendar (with what to share; `writerWithoutPrivateAccess` names its own option), and its remaining ops are dropped for this run; if the hub may write there, it is that event's own refusal: a link error with backoff, and the calendar isn't marked. **404** `notFound` on the calendar (the probe) → `no_access` likewise.<br>Any other 403 → a link error with Google's reason.<br>**401** → get a new token once and try again, else `auth`.<br>**400** → a link error with Google's message (a bug on our side, shown in Settings).<br>**5xx**, a timeout or a network error → one retry after 1 s, else a link error. These never change `calendars.status`.<br>The reason is read from `error.errors[0].reason`, `error.status` and `error.details[].reason`. **412** can't happen, because no `If-Match` is sent: the last write wins, by design. |

### 3.6 Limits, first sync, bursts and backoff
- **Volume.**
  - A household like the test one has about 10 weekly series × 2 days a week × 9 weeks ≈ 180 occurrences.
  - With copies for people along, about 270, plus around 50 tasks and 20 project markers: the first full copy is about 350 inserts.
  - After that, each day the window gains about 6 new events, plus whatever was edited.
  - Reads: about 7 calendars every 15 minutes, about 700 calls a day.
- **Per run:** at most 60 writes and 10 calendars read (at most 4 pages each), with no call starting after 30 seconds and at most 4 calls a second. So at most about 120 calls in a run, far inside 600 a minute per user (G6).
  - The first full copy takes about 6 runs, ≈ 30 minutes, nearest days first, and starts only as each calendar is approved. Hundreds of events are never created at once (the brief's warning about abuse limits).
- **Bursts.** Plans compare states, not changes. Twenty edits to one event in 5 minutes are one update; an event added and deleted between runs is no call at all. Changing the household's time zone rewrites every event, which spreads over a few runs.
- **Backoff.**
  - A rate-limit answer stops the run and pauses all Google calls: 10 minutes, doubling at each new one (`pause_step`), at most 1 hour.
  - Failures of single items back off on their own link (§3.3).
- **Two runs at once** (cron and Sync now) can't happen: the lease stops the second. If a lease outlives a crash, it expires after 10 minutes.

### 3.7 Schedule
- `cron.sql` gains `hub-calendar` at minutes `2,7,12,17,22,27,32,37,42,47,52,57`: every 5 minutes, away from the quarter-hour `hub-digest` runs.
- The job posts `{"action": "calendar"}` with the same `x-hub-cron` header, read from the same two Vault secrets (`hub_cron_secret`, `hub_jobs_url`), with `timeout_milliseconds := 60000`.
- `hub-cron-cleanup` already covers `hub-%` jobs.
- Reads happen at most every 15 minutes, by `read_at` (§5.1), so a change in Google reaches the hub within about 20 minutes.
- A change in the hub reaches Google within about 5 minutes. Hearth then adds its own delay (step F.5 measures it).
- No database triggers and no `pg_net` call on every edit: 5 minutes is fast enough for a wall, and it keeps the design to one moving part.

### 3.8 Why an action in `hub-jobs`, not a new function
- It already has what the calendar needs: the cron secret and its constant-time check, the two Vault secrets, `verify_jwt = false` in `config.toml`, the admin check through `whoami()`, the deploy routine and the real-handler hookup in `tests/realdb/lib.js`.
- A second function would need a second Vault URL, a second deploy, and another place for the owner to look.
- Each action runs in its own request, so the calendar code never runs inside a morning-email run. The only shared risk is a broken deploy, and `tests/run.sh` guards against that. The calendar job doesn't write `job_runs`, so the morning email's status in Settings is unchanged.

## 4. Routing: which calendar each item goes on

"Has a calendar" means the person is active and has a row in `calendars` with `writes`. People without a calendar get no copy, and nothing falls back to Family for them: the Family column would fill up with other people's items. Settings lists them under **Not on Google** (§6.5). Routing doesn't depend on a calendar's status or approval: those only hold the writes back (§3.3).

| # | Item | Goes on | Title |
|---|---|---|---|

## 5. Reading Google: events typed into Google

### 5.1 What is read
- Every mapped calendar is read: the ones the hub writes (people type straight into "Hub – Jordan" on a phone), the family account's main calendar, and any other read-only ones.
- Each is read at most every 15 minutes, with `events.list` (G7):
  - `singleEvents=true`, `orderBy=startTime`, `showDeleted=false`, `maxResults=2500`, `eventTypes=default` (no reservations from Gmail, out-of-office, working-location, focus-time or birthday events);
  - `timeMin`/`timeMax` from `calendar_read_due()`, and `timeZone` set to the household's zone;
  - `fields=accessRole,summary,nextPageToken,items(id,status,summary,location,start,end,visibility,recurringEventId,updated,organizer/self,attendees(self,responseStatus),extendedProperties/private)`. No email address is asked for, and no description.
- It follows `nextPageToken` for up to 4 pages, checking the reads' 20 seconds before each (§3.4).
  - If any page fails, nothing is stored: the cache and `read_at` stay as they were.
  - If pages remain after 4, or more than 1,000 events would be kept, what was read is stored with `p_complete` false (§5.2), and Settings says the calendar is cut off.
- **No `syncToken` and no push channels.** A full window every 15 minutes is about 700 small calls a day, and it repairs itself.
- `hub-jobs` turns each item into a small object (id, status, title, place, start, end, visibility, whether it repeats, `updated`, `organizer.self`, the calendar's own attendee answer, the `homehub` properties, and the content hash) and leaves every rule to `calendar_store_events`, so the db tests cover them.

### 5.2 Storing, and putting back the hub's own events
`calendar_store_events(p_calendar, p_google_id, p_from, p_to, p_name, p_access, p_complete, p_events, p_seen)`:
- **Nothing happens** if the row is gone or its `google_id` is no longer `p_google_id` (it was re-pointed during the run).
- **Status.** Sets `google_name`, `access_role`, `checked_at` and, for a complete read, `read_at`. Then:
  - a calendar the hub only reads: `ok`, if the access role is `reader` or better (`writerWithoutPrivateAccess`, Google's "Make changes (see private events as free/busy)", reads too);
  - a calendar the hub writes: `ok` only if its Google name, trimmed, starts with "Hub" (any case), **and** its access role is `writer` for the service account or `owner` for OAuth (`calendar_sync.auth`). Otherwise:
    - a name that doesn't start with "Hub" → `error`: "This calendar isn't named 'Hub …'. The hub writes only to calendars whose name starts with Hub. If it is the right one, rename it in Google." This replaces a check for the name "Hearth": Hearth's naming is undocumented and anyone can rename a calendar, so the rule says what may be written, not what may not;
    - `reader` or `freeBusyReader` → `no_access`: "Share it with <account> and choose Make changes and see event details";
    - `writerWithoutPrivateAccess` → `no_access`: "Shared with 'Make changes (see private events as free/busy)': Home Hub can't change its private items there. Share it with <account> and choose Make changes and see event details." (The hub writes private items; with that role it couldn't change them again.);
    - `owner` for the service account → `error`: "Share it with Make changes and see event details, not Make changes and manage sharing".
  - The sharing options are named as Google Calendar's sharing menu names them: "See only free/busy", "See event details", "Make changes (see private events as free/busy)", "Make changes and see event details", "Make changes and manage sharing".
  - So a read never clears a refusal by itself: only a read that sees the right access role does, which is what fixing the sharing produces.
- **Which items are kept.** An item is dropped (and counted) when:
  - its `status` is `cancelled`;
  - it is an invitation nobody accepted: neither `organizer.self` is true nor the calendar's own attendee entry says `accepted` or `tentative`;
  - it is the hub's own: `homehub` is set and its id matches `^hh[0-9a-f]{32}$` (those go to `p_seen`). A `homehub` event with any other id (someone used **Duplicate** in Google) is kept as an ordinary Google event;
  - its id is in `calendar_links` for that Google calendar (a second guard against copying back);
  - it can't be read (bad dates and the like): skipped and counted, never a reason to fail the store.
- **What is kept**, after `private.clean_text(p_text, p_max)`:
  - the title and place, except that a private or confidential event is stored with title `''` and no place, and shows as "Private item" to everyone. Google's own Private probably hides nothing on the wall, because Hearth reads as the calendar's owner: the README says to use the hub's Private;
  - for an all-day event, `start_day` is `start.date` and `end_day = greatest(start_day, end.date − 1)`;
  - for a timed event, `start_day` and `end_day` are the household's days of `start_at` and of the instant just before `end_at`, with `end_at = greatest(start_at, end_at)` and `end_day = greatest(start_day, …)`, so a zero-length event at midnight or one with no end can't break the check;
  - whether it repeats (`recurringEventId`).
- **Replaces** that calendar's `google_events` rows (for an incomplete read: replaces the days it covered, and keeps the rest).
- **Changes made in Google to the hub's events are put back.** Only for calendars the hub writes and may write now (`ok` and approved with **Start copying**), only for complete reads, and only for links that are `ok`, were written (`synced_at` set), whose `[day, end_day]` overlaps the read window, and that the plan will write again (still in `private.calendar_desired` for the window: not a stale project's link, nor one about to be deleted), so that what is recorded as put back really is:
  - **Edited in Google:** `updated` differs from the link's `google_updated` (a cheap first filter) **and** the content hash differs from the link's `google_hash`. The content hash is SHA-256 of Google's own `summary`, `location`, `start`, `end` (dates as written, times as instants), `visibility` and `status`, computed by `google.ts` the same way from a write's answer and from a read. So a change of reminders or colour (which some phone apps make, and which may move `updated`) isn't a repair, and OAuth's PUT never wipes the family account's own reminders for nothing.
  - **Deleted in Google:** the event didn't come back at all.
  - In both cases `hash := null`, so the next plan rewrites it (a deleted one is brought back by `status: "confirmed"`), and `repaired_at`, `repair_kind` and `repairs` are set. `repairs` starts again at 1 when the last repair is more than 24 hours old. The fourth repair of one link within 24 hours sets it to `error` ("Google keeps changing this event") with `next_try_at` a day away; a change to the item in the hub (a new hash) tries again at once.
  - Settings lists the 5 latest ("Changed in Google and put back"), and the parents' next email says so (§5.6).
- **Orphans.** Only on calendars the hub writes, only for complete reads: an event marked `homehub` with an `hh…` id but no link (a run died between Google and `calendar_record`, say) gets a link row with `hash` null, `synced_at` now, its `day` and `end_day`, `base_id` from `homehub_base` (its own id if that is missing, invalid or already linked), and the item fields from its extended properties, read with safe casts: a bad value skips that one event, never the store. The plan then updates it if it's desired and deletes it if not. On a calendar the hub only reads, `homehub` events are simply kept out of the cache.
- Returns `{kept, skipped, seen, repaired, adopted}`.

## 6. Signing in to Google, secrets, errors, Settings

### 6.1 Service account (`google.ts`)
- **Reading the key.** `GOOGLE_SA_JSON` is read with a literal `deps.env('GOOGLE_SA_JSON')` (the docs check finds secrets that way). It is trimmed; if it doesn't then start with `{`, it is base64-decoded first. Then it is JSON.parsed.
  - It needs `client_email` and a `private_key` in PEM; `private_key_id` is kept for Settings.
  - A `\n` written out as two characters becomes a newline.
  - `token_uri` defaults to `https://oauth2.googleapis.com/token`.
  - Anything else gives `stop: 'config'` with "GOOGLE_SA_JSON isn't a service-account key: paste the whole downloaded file". Errors from reading the secret or exchanging the token are never passed through `message()`.
- **The JWT.**
  - Header `{"alg":"RS256","typ":"JWT"}`.
  - Claims `iss` = `client_email`, `scope` = `https://www.googleapis.com/auth/calendar.events`, `aud` = the token URI, `iat` = now, `exp` = now + 3600.
  - Signed with WebCrypto: `crypto.subtle.importKey('pkcs8', der, { name: 'RSASSA-PKCS1-v1_5', hash: 'SHA-256' }, false, ['sign'])`, then `sign`, all base64url.
  - It is POSTed as a `URLSearchParams` body: `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=<jwt>`.
  - About 30 lines, no library.
  - The scope only limits the hub's own tokens. Whoever holds the key can ask for any scope, so the real limit is how each calendar is shared: only the Hub calendars, with **Make changes and see event details**, which can't change sharing (§7.2).
- **Caching.** The access token is kept until 5 minutes before `expires_in` runs out, keyed by a fingerprint of the credential, so a warm function reuses it and a changed secret never gets the old one. `resetTokenCache()` is exported for the tests. At worst there is one token request per run, about 300 a day.
- `calendar_signed_in` records `client_email` and `private_key_id`. Settings shows the address, so the admin knows what to share calendars with.

### 6.2 OAuth fallback (built only if a gate fails)
- Used when `GOOGLE_SA_JSON` is unset and `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` and `GOOGLE_OAUTH_REFRESH_TOKEN` are all set.
- The scope is `https://www.googleapis.com/auth/calendar.events.owned`: events on calendars the family Gmail **owns** (the Hub calendars, its main calendar, Hearth's). Not `calendar.events`, which reaches every calendar shared with the account for editing, such as a team or carpool calendar. So on OAuth, "Calendars to read" can only hold calendars the family Gmail owns.
- POST `grant_type=refresh_token` to `https://oauth2.googleapis.com/token`, cached the same way.
- `invalid_grant` gives `stop: 'auth'` with "Google's sign-in for Home Hub was revoked or expired: make a new refresh token (README)".
- A token used every 5 minutes never hits the 6-month unused limit (G2).
- `calendar_sync.auth = 'oauth'` and `account` is null: Settings says "Signed in to Google as the family account". A writing calendar needs access role `owner`.
- **Revoking it** (README and §7.3): at myaccount.google.com → **Security → Your connections to third-party apps & services → Home Hub → Delete all connections**; in the Cloud project, add a new client secret and delete the old one; then make a new refresh token (§1.4 step 3).
- There is no Connect Google button in the hub (a non-goal): the refresh token stays in Supabase's secrets, not in a table.

### 6.3 Secrets

All are optional for `hub-jobs`: the morning email works without any of them.

| Secret | When |
|---|---|
| `GOOGLE_SA_JSON` | The service-account path: the whole key file |

### 6.4 Errors, and where they show
- Google's error messages are cleaned and cut to one line of at most 300 characters. Anything shaped like a token (`ya29.…`, `1//…`, a JWT) is removed from them.
- **Never logged or stored:** keys, tokens, request headers, request bodies, event titles, and Google's replies. Console output and pg_net responses carry counts and fixed codes only.

| Problem | Where it shows |
|---|---|
| Not set up, bad secret, the API not turned on, Google refused the key or token, database error | `calendar_sync.last_stop` and `last_error` (fixed messages); a red line in Settings with the fix; the parents' email warning (§5.6) |
| A calendar can't be reached (not shared, shared read-only, wrong ID, not named "Hub…") | `calendars.status` and `status_detail`; the calendar's row in Settings |
| One item couldn't be written | `calendar_links.status = 'error'`, `error`, `next_try_at`; Settings' problem list (admins); the parents' email after 24 hours |
| Changed in Google and put back | `calendar_links.repaired_at`, `repair_kind`; Settings (admins); the parents' next email |
| Google said slow down | `calendar_sync.paused_until`; Settings: "Paused by Google until 3:40pm" |
| The job isn't running (cron.sql not run again, or the function deployed with JWT verification on) | Settings: "Last synced more than 30 minutes ago. The calendar job may not be scheduled: run supabase/cron.sql again (README)." The SQL to look at pg_net's log is in the README, not on the page |

`hub-jobs` `{action: 'calendar_test', calendar_id}`, for admins:
1. It reads the row as service_role (a uuid naming an existing row, or 400).
2. It lists 1 event (`maxResults=1`, `fields=summary,accessRole`), which gives the calendar's Google name and the access role, and applies §5.2's status rules. On a calendar the hub writes whose name or role fails them, it stops there: nothing is inserted.
3. On a calendar the hub writes that passes (gate 2): it adds an event with id `hhtest` plus 16 random hex characters (all-day on 2001-01-01, so no wall or phone ever shows it), deletes it, PUTs the same id with `status: confirmed` (expecting 200: a deleted event comes back), reads it back and compares the content hash with the PUT's answer, and deletes it again. Each step's result is in the answer.
4. It records the result with `calendar_mark(…)`, and answers `{ ok, status, message, name, role, steps }`.
- Messages:
  - 403 or role `reader`: "Home Hub can't change this calendar. In Google Calendar, share it with <account> and choose Make changes and see event details."
  - Role `writerWithoutPrivateAccess` on a calendar the hub writes: §5.2's message, naming "Make changes (see private events as free/busy)" and the option to choose instead. On a calendar the hub only reads, that role reads: `ok`.
  - Listed with the writer role, yet the insert gets a 403 (gate 2 failing, §1.2): "Shared correctly, but Google won't let Home Hub add an event to it: tell Claude."
  - 404: "No calendar with this ID, or it isn't shared with <account>."
  - For OAuth, "isn't in the family account".
  - If the PUT doesn't bring the event back, or the hashes differ: "Google answered differently than expected: tell Claude." The reconciler still works in both cases (a new id after a clash; a repair at most 3 times a day), but the design assumed otherwise.

## 7. Security and privacy

1. **The wall is public in the house.** Everyone sees it: the family, the helper, guests and workers. What the helper sees there is decided by which Hub calendars Hearth shows (step F), not by the hub.
   - Copied: titles, times, an event's place, a project job's name, a linked directory entry's name and business phone.
   - Never copied: notes and a day's own note; private items' titles, places and details ("Private item" with `visibility: private`); health tasks' titles (rule 7b); the family's phone numbers and emails; account numbers (the calendar code never reads `contractor_secrets`; `agenda`, `late_items()` and `task_dates` don't carry them); My day and confirmation links.
   - The forms' Private label says where it applies: "on the wall, in Google and to kids and helpers".
2. **Least privilege in Google.**
   - The service account reaches only the calendars shared with it. Because whoever holds a key chooses its scope, the real limit is the sharing: **Make changes and see event details** on the Hub calendars only, which can't change sharing, and **See event details** on calendars it reads. A service account found with `owner` (Make changes and manage sharing) is refused (§5.2), and so is `writerWithoutPrivateAccess` on a calendar it writes.
   - The hub writes only to a calendar that: is a `calendars` row with `writes`; is a secondary calendar (`@group.calendar.google.com`); has a Google name starting with "Hub", checked on every read; was last seen with the right access role; is `ok`; and has been approved with **Start copying**. Test checks name and role before it inserts anything.
   - OAuth, if built, asks only for `calendar.events.owned` (§6.2).
   - No attendees, so no invitations or emails go to anyone (G1). No reminders (G5).
3. **Nothing goes on the wall unseen.** v2 items were written when only signed-in grown-ups could see them. Each calendar's first copy waits for an admin to look at everything it copies (the preview covers the job's whole window, yesterday to 60 days ahead, with each event's place and directory line) and press **Start copying**; later days reach the wall as the window reaches them, as any new item does. Members get a one-time notice on Today.
4. **The key is a password for every Hub calendar.**
   - It lives only in Supabase's Edge Function secrets, never in the repository, the database, a chat or a log. The downloaded file is deleted after step B. Claude never receives the file or its contents.
   - The Cloud project is in a parent's own personal account (not the shared family Gmail, which more people can sign in to), with the other parent as a second Owner, both with 2-step verification.
   - Settings shows the last 6 characters of the key's id (`private_key_id`), and the Cloud project's **Keys** tab must list exactly one key, ending the same way.
   - To rotate it: Cloud Console → the service account → **Keys → Add key**, replace `GOOGLE_SA_JSON`, delete the old key, and check that Settings shows the new id. If it leaks, delete it in Cloud Console at once; that revokes it.
5. **Row-level security and grants on the new tables:**
   - `calendars`: members read, admins write the setting columns only (column grants).
   - `google_events` and `calendar_sync`: members read. `calendar_links`: admins read.
   - Only the job functions (`service_role`) write the last three; `authenticated` has no insert, update, delete, truncate, references or trigger on them.
   - All four are revoked from anon. The tests' role matrix covers each, and checks the privileges themselves (§8.1).
6. **Anon gets nothing new.** There is no new anon function. My day gains only the Google events of §5.4's right-hand column, through the existing `get_person_day(p_token)`: never a read-only Family calendar unless it is marked **Show to kids**, and never Family's for a helper. A read-only calendar an admin gives to a person (**Whose**) is that person's, and reaches their My day like their own Hub calendar; Settings says so where the calendar is added.
7. **Reading is opt-in per calendar, and kept small.**
   - Only calendars an admin maps are read.
   - What's read is kept to title, place, times and privacy, after cleaning. A Google event marked private or confidential is stored without its title or place, so no member sees it, whatever page they use.
   - Only ordinary events (`eventTypes=default`), and only ones the calendar made or accepted: an invitation from a stranger never reaches an email or a text to the helper.
   - A place from Google is always shown as plain text, never as a link.
   - When a calendar becomes `no_access`, its cached events are deleted in the same transaction. When its Google ID changes, they stop showing at once and the next run deletes them. Cached events no read has refreshed for 24 hours are deleted too.
8. **Errors and statuses hold fixed messages and at most Google's one-line reason**, with token-shaped strings removed (§6.4). Members can read a calendar's status; the errors of single items (`calendar_links`) are for admins only.
9. **People leaving.** `remove_person` deletes the person and the `calendars` row with them, and the hub's events come off the calendar. The sharing with that person's own Google account stays, so the README's "When a helper leaves" checklist says: give the next helper a new My day link; stop sharing the calendar with the old helper's account; delete her Hearth profile; and make a new Hub calendar for the next person rather than reusing the old one. Settings reminds admins for anyone inactive who still has a calendar (§6.5).
10. **Sharing with phones (step G):** personal accounts only, never a school or work account, whose administrators can read what is shared with it. Never "Make available to public"; never hand out the "Secret address in iCal format", and reset it if it was ever used.
11. **Accepted risk:** any member can still clear Private on someone else's item, or change a directory phone number, and that reaches the wall within 5 minutes. Members are the grown-ups of the house, and every change is recorded in `updated_by`. Only admins map calendars, approve copying, and run Test or Sync now.
12. **The family Gmail now holds the hub's calendars:** 2-step verification (setup §1.3).

## 11. 0010: a shared calendar sorted by Hearth person

The kitchen wall (Hearth) keeps every event made on it in **one** Google calendar, "Hearth Calendar", in the family Google account, for everyone. This settles the open point of §5.5. Seen on the family's calendar since: Hearth marks whose event it is by adding that Hearth profile as a **guest**, with an address like `jordan@team-example-0000` (`<profile>@team-<family>-<digits>`, with no dot after the @, so no real mailbox). A kid's piano lesson has the kid's profile; an adult's furnace check the adult's; a house visit has `familyanddogs@team-…`, for Hearth's "Family and dogs" profile. An event can have several.

Before 0010 the hub can read that calendar only as one person's or as Family. As Family, every person's events become everyone's: all of them reach the grown-ups' emails, and a kid gets none of them (or, with **Show to kids**, all of them, never sorted), so his lessons never become his busy time.

What the owner asked for ("build it", for everyone): the hub reads that calendar and sends each event to its person by its Hearth guest. The parents match each guest once in Settings: to a family member, to Family, or left to the grown-ups. The family keeps adding events on the wall as now. The hub never writes to that calendar.

It is migration `0010_hearth_people.sql` (schema 10), the site, and `hub-jobs` (`calendar.ts` only). No new Edge Function, secret, Vault secret or `cron.sql` change. It comes after `0009_school_keys.sql` (schema 9) and refuses to run without it. Examples use the household of this doc: Alex and Morgan (parents), Sam (adult), Jordan (kid), Taylor (helper); the tags are `jordan@team-example-0000`, `sam@team-example-0000`, `taylor@team-example-0000`, `familyanddogs@team-example-0000` and `dogs@team-example-0000`.

### 11.1 Decisions on one page

- **A switch per calendar:** `calendars.sort_by_guest`, **Sort by Hearth person** in Settings, only on a calendar the hub reads as Family. 0010 leaves it off everywhere, so nothing changes until a parent turns it on.
- **A tag** is a guest address shaped like Hearth's (`private.hearth_tag(p_email)`, §11.3). Nothing else from a guest list is kept: every other address is dropped inside `hub-jobs`, before anything is stored or sent. Google is asked for guest addresses only for calendars with the switch on.
- **Stored:** each cached event's tags (`google_events.guests`, at most 16), and per calendar the tags seen and what each is matched to (`hearth_tags`: a person, Family, or **Grown-ups only**, the default), with first and last seen.
- **Routing is worked out when the event is read from the cache**, in the replaced `private.google_item(g, c)` and `private.google_for(p_person, p_from, p_to, p_grown_up)`. A match works at once, with no new read, and every place that takes Google events (the pages, My day, texts, the email, busy time, the tutor's view, the coach view) follows without a change of its own.
- **The rule:** an event goes to everyone its tags reach. A person's tag reaches that person. A Family tag reaches who a read-only Family calendar with Show to kids reaches: every parent's and adult's email, and every kid; never a helper. A tag that reaches nobody (Grown-ups only, new, or matched to someone off the family list) adds nobody. An event that no tag reaches is the grown-ups' only, as on a read-only Family calendar without Show to kids.
- **Matching is for the parents only**, through `set_hearth_tag(p_tag, p_to, p_person)`. Members see the tags and the matches, read-only.
- **Schema 10.** The site goes live first, then `hub-jobs`, then 0010 (§11.9).

### 11.2 Data

```
calendars.sort_by_guest  boolean not null default false     -- "Sort by Hearth person"
  check (not sort_by_guest or (kind = 'family' and not writes))  -- only a calendar the hub reads as Family
  check (not (sort_by_guest and for_kids))                       -- the matches replace Show to kids
  column grant: authenticated may update it (row-level security: admins only, as for for_kids); not insert

google_events.guests  text[] not null default '{}'          -- the event's tags: each one private.hearth_tag's
  check (cardinality(guests) <= 16)                         --   answer, distinct, sorted; '{}' on every
                                                            --   calendar without the switch

hearth_tags (the Hearth people seen on a sorted calendar, and whose events each one's are)
  id          uuid PK default gen_random_uuid()            -- set_hearth_tag's key
  calendar_id uuid not null → calendars on delete cascade
  tag         text not null check (tag ~ '^[a-z0-9._+-]{1,64}@team-[a-z0-9-]{1,120}$')
  name        text generated always as (split_part(tag, '@', 1)) stored   -- what Settings shows: "jordan"
  person_id   uuid → people on delete set null             -- matched to this person
  to_family   boolean not null default false               -- matched to Family
                                                           -- neither: Grown-ups only (the default)
  first_seen  timestamptz not null                         -- the store that first found it (private.now())
  last_seen   timestamptz not null                         -- the last store that found it on a kept event
  matched_at  timestamptz                                  -- the last set_hearth_tag; null = never matched ("New")
  matched_by  text                                         -- public.current_email() then
  unique (calendar_id, tag)
  check (not (to_family and person_id is not null))
  check (last_seen >= first_seen)
  RLS: members select ("Family can see the Hearth people"); no write policy.
  Grants: revoke all from public, anon, authenticated; grant select to authenticated.
  Written only by calendar_store_events (service_role) and set_hearth_tag (SECURITY DEFINER).
```

**What is stored, and when** (all by `calendar_store_events`, in the store of one read):
- `guests`, for each kept event, only while the calendar row's `sort_by_guest` is on at that store: the `guests` array hub-jobs sent, each entry through `private.hearth_tag(p_email)`, nulls dropped, distinct, sorted, the first 16. On any other calendar it is `'{}'`, whatever was sent. A private or confidential Google event keeps its tags (they decide whose day it is), but not its title or place, as now.
- `hearth_tags`, on a sorted calendar: every tag on a kept event that the calendar doesn't have yet is added (`first_seen` = `last_seen` = now), while the calendar has fewer than 50 rows; past 50 a new tag is left out (its events still carry it, and reach nobody through it). Every tag it already has that is on a kept event gets `last_seen` = now. Only kept events count (not cancelled ones, invitations nobody accepted, or the hub's own).
- Nothing about tags is in `calendar_links`, `calendar_sync`, `calendars.status_detail` or any message.

`private.calendars_tidy()` is replaced with three additions, all before the checks run: a calendar that isn't read-only Family has `sort_by_guest` set to false (so changing **Whose** or switching a row to writing never trips the check); a sorted calendar has `for_kids` set to false; and a change of `sort_by_guest` clears `read_at` (so the next run reads it first, with or without the guests) and counts as an admin's edit (it keeps `updated_at` moving, unlike the job's own writes).

**Life cycle:**

| What happens | `hearth_tags` (tags and matches) | `google_events.guests` |
|---|---|---|
| **Disconnect** (the row is deleted) | Deleted with it (cascade) | Deleted with it (cascade) |
| **A new Google ID** on the row | Kept. A tag names the Hearth team, not the Google calendar, so a match only ever applies to events that carry that exact address | The old rows stop showing at once and the next run deletes them (§2); the next read stores the new calendar's |
| **Switch turned off** | Kept, and not used: at once the calendar is an ordinary read-only Family calendar again (Show to kids can be turned on). Turning it on again uses them | Not used at once; the next read (due at once: `read_at` is cleared) stores `'{}'` |
| **Switch turned on** | As they were | None until the next read (due at once), so until then every event reaches the grown-ups only |
| **A person made inactive** | Kept; while they are off the family list their match reaches nobody (§4 rule 12). Back on the list, it works again | — |
| **A person removed** (`remove_person(p_person)`) | `person_id` becomes null: Grown-ups only | — |
| **The calendar `no_access`** | Kept | Deleted with its cache (§2) |
| **A tag that reaches nobody** (Grown-ups only, chosen or not), not seen for 90 days | Deleted by that calendar's next complete read, switch on or off | — |
| **A matched tag** not seen for a while | Kept until Disconnect, so a lesson that comes back after the summer finds its match | — |

Cached events, and so their `guests`, live as §2 says: replaced by every read, deleted 24 hours after the read that stored them.

### 11.3 hub-jobs: reading the guests (`calendar.ts`)

- `calendar_read_due` answers one more column, `guests` (the row's `sort_by_guest`).
- **What is asked.** For a row with `guests` true, the list call's `fields` is `READ_FIELDS_GUESTS`: `READ_FIELDS` with `attendees(email,self,responseStatus)` in place of `attendees(self,responseStatus)`. Every other calendar is read with `READ_FIELDS`, as now: no address is asked for. `maxAttendees` is not sent (with it, Google answers a longer guest list with only the calendar's own entry).
- **What is kept.** `hearthTags(list)`: of the first 100 entries, it skips the calendar's own (`self` true), takes `email` when it is a string, trims and lowercases it, and keeps it only if it matches `HEARTH_TAG = /^[a-z0-9._+-]{1,64}@team-[a-z0-9-]{1,120}$/`, the pattern of `private.hearth_tag(p_email)`. It removes duplicates, sorts, and keeps the first 16. Nothing is rewritten into a tag: an address is kept exactly as lowercased, or dropped. A guest's real address, the family's own, a room's or the calendar's never leaves that function.
- `storeItem(it, guests)` adds `guests: hearthTags(it.attendees)` only when `guests` is true; otherwise the item has no `guests` key, as now. The calendar's own answer (`response`) is read as now.
- **Where the tags go:** only into that calendar's `p_events` in `calendar_store_events`. Never into a log line, an error, `calendar_mark`, `calendar_finish`, the run's answer or another call. Console output and pg_net's log keep counts and fixed codes only (§6.4).
- **Older pieces keep working.** The new hub-jobs on schema 9: `calendar_read_due` has no `guests` column, so no address is asked for and nothing changes. An older hub-jobs on schema 10: it ignores the new column and sends no guests, so a sorted calendar's events have no tags and reach the grown-ups only (it fails closed) until hub-jobs is updated. `calendar_store_events`' answer is unchanged.
- `calendar_test` is unchanged: it never asks for guests.

### 11.4 Routing

- `people`: the active people its tags are matched to (`hearth_tags` of that calendar whose `tag` is in `g.guests` and whose `person_id` is an active person, `private.active_person(p_id)`), each once, in family-list order (`sort_order`, `name`, `id`), as `private.names(p_ids)` lists them;
- `family`: whether any of its tags is matched to Family.

For any other row it gives `'{}'` and false.

### 11.7 Privacy and security

1. **What a tag shows:** a Hearth profile's name (usually a first name, or "familyanddogs") and the family's Hearth team ("team-<family>-<digits>"). It is not a mailbox and opens nothing.
2. **Who sees tags:** members (the signed-in grown-ups), through row-level security on `hearth_tags` and `google_events`; Settings shows only the part before the @. Kids, the helper, the tutor and anyone signed out never do: `agenda_item` has no field for them, so no token function, My day, text, email or tutor view carries one. Tags never leave the database: not in an email, a text, a Google write or a log.
3. **Only this calendar's addresses are asked for, and only tags are kept.** `hub-jobs` asks Google for guest addresses only for calendars with the switch on, and drops every address that isn't shaped like a Hearth tag before anything is stored or sent (§11.3). The service account could already see them (it reads this calendar with See event details); the hub now looks, on this one calendar, and keeps only Hearth's.
4. **The hub never writes this calendar.** A sorted calendar is read-only by constraint (`not writes`); the hub writes only to calendars named "Hub …" (§5.2); and `private.calendar_desired(p_from, p_to, p_site)` never reads Google events. Nothing of it is copied anywhere.
5. **Kids and the helper:** a person's tag reaches that person only; Family's never reach a helper; grown-ups-only events never reach a kid or a helper, nor anyone's My day. A kid's tutor sees his busy time without titles (as now), and in the coach view only events matched to him alone.
6. **Fails closed.** A new tag, an unmatched one, one matched to someone off the family list or removed, an older hub-jobs, a tag shape the pattern doesn't know, a calendar not read yet: each reaches only the grown-ups.
7. **Anon gets nothing new.** No new anon function. `get_person_day(p_token)` and the other token functions gain only the rows §11.4 gives that person.
8. **Only parents match** (`set_hearth_tag`, definer, `private.is_admin()`), and every member can see every match, so a wrong one is visible. The switch is a column grant with the admins-only update policy, as Show to kids.
9. **Accepted:** anyone at the wall can make an event for any profile, and it reaches that person's My day with the title as typed (cleaned, as every Google title is). That is the same as typing into a person's calendar today; the wall is in the house. A kid's own wall events reach his coach view by title, as his own calendar's do.
10. **No labels:** a tag is a profile's name; nothing new can carry a label, and the label-word check covers the new files.
