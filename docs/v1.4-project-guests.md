# Home Hub v1.4: project guests (draft for decision)

Status: design only. Nothing here is built until the decisions in §7 are answered.

A **project guest** is someone outside the family, such as an interior designer, who signs in with an emailed code like the family and sees only the projects a parent assigns them. In the examples the guest is Morgan, a made-up designer, assigned the made-up "Kitchen" project.

## 1. Recommendation in one line

Keep the default: a guest is **not a member**. A new `guests` table and a `project_guests` table give a guest their own narrow policies on `projects` and nothing else, so every existing `private.is_member()` policy keeps them out without being touched.

Rejected alternatives:

- **A `guest` role in `members`.** Every `is_member()` policy (36 tables) would let the guest in; each would need rewriting. Much larger change, much larger risk.
- **An edit link with no sign-in** (like the tutor link). Weaker: a forwarded link is a working login, and it can't be revoked per person without a new link.
- **A second Supabase project.** Two schemas, two deploys and sync between them, for one user. Overkill.

## 2. What a guest can and can't reach (audit of schema 10)

| Surface | Today, for a signed-in non-member | After 0011 |
| --- | --- | --- |
| 36 tables | RLS on all, every policy `is_member()` or `is_admin()`; `people_confirm` revoked | Unchanged. Only `projects` gets guest policies, plus the two new tables |
| 31 signed-in functions | Security-definer ones check `is_member()`/`is_admin()`; security-invoker ones (`agenda`, `day_text`, `heads_up`, `late_items`, `google_items`, `shopping_list`, `homework_week`) read through RLS and return nothing | Unchanged. `agenda` would show the guest only their own project's task dates (RLS), never events or tasks; the guest pages don't call it |
| 22 token functions | Need a My day, confirmation or tutor token; a guest has none | Unchanged |
| `private` helpers granted to signed-in users | `is_member`, `is_admin`, `tz`, `food_other` (text only), `has_secrets(uuid)` (a yes/no for a directory id the guest can't learn) | Unchanged |
| Directory and account numbers | `contractors` member-only; `contractor_secrets` admins only | Guest reads a stripped list through one function (§4); never `contractor_secrets` |
| Share links | `get_shared_project` is anon-only and already public by design | Guest sees and copies the link a parent turned on; can't turn it on, off or rotate it |
| `whoami()` | Returns null, so the site shows "not on the list" | **Not changed.** `send-email` treats any non-null `whoami()` as family; extending it would let a guest send hub email. A separate `guest_whoami()` instead |
| `send-email`, `hub-jobs` | 403 (whoami null / not admin) | Unchanged: 403 |
| Morning email, My day | Built from `people`; a guest isn't a person | Unchanged. A guest gets no hub email (§6) |
| Sign-up hook | `hook_family_only_signup` allows only `members` emails, so a guest's first sign-in is refused | 0011 replaces it to also allow an **active** guest. Same hook name, no dashboard change |
| Google Calendar and the wall | Project task dates sync to the family calendar when "Show in Home Hub calendar" is on | A guest's schedule edits flow there too (intended). Only parents change that switch |

## 3. Data model (migration 0011)

- `guests (email pk, name, active, created_at, created_by)`. An email can't be both a guest and a member (checked in the save function and a trigger on both tables).
- `project_guests (project_id, guest_email, added_at, added_by)`, cascade on project delete.
- `projects.documents_url text`: the shared folder's address. Only `https://drive.google.com/…` accepted.
- `project_contacts (project_id, contractor_id)`: the contractors on a project. Filled automatically from every contractor the project's schedule links (trades and tasks); a guest can add new ones (§4).
- `private.is_guest_of(project_id)`; `public.guest_whoami()`; parent functions `save_guest`, `set_project_guest`, `remove_guest`; guest functions `guest_contacts`, `guest_save_contact`.
- `hub_schema_version()` returns 11.

Guest policies on `projects`: select and update only where `is_guest_of(id)`. A guard trigger refuses a guest change to `owner_id`, `on_calendar`, `sharing_enabled`, `share_token`, and any schedule link to a contractor not on the project. No insert or delete for guests.

## 4. What the guest manages

- **Schedule**: the Gantt phases, tasks, dates, statuses and trades of each assigned project; name, summary and status.
- **Contractors on the project**: name, company, trade, phone, email, website. Never account numbers, directory notes or addresses, and never the rest of the directory. They can add a new contractor (it joins the family directory and the project) and edit ones on their projects that have no account details saved.
- **Documents**: one "Documents" button on the project page opening the Drive folder; parents and the guest can change the address.
- **Messages**: the project's text, WhatsApp and Share buttons work from the guest's own phone. "Send email now" (the hub's `send-email`) is hidden for guests.

## 5. Assigning and removing access

1. Project page → Settings → **Guest access** (parents only): add a name and email, or pick an existing guest. Saved, the guest can sign in.
2. End of job: the same place → **Remove**. Access ends on the guest's next request (RLS checks every call); no sign-out needed.
3. Settings → **Guests** lists every guest and their projects, with **Remove guest** (deactivates them everywhere). Their Supabase login can be deleted by hand in the dashboard; the doc will say how.

## 6. The guest's hub

- **Pages**: Projects only. One assigned project → straight to it; none → "No projects assigned to you right now."
- **Header**: "Home Hub · Projects", the guest's name, Sign out. No bottom bar, no Today, Calendar, Tasks, Food, Homework, Family, Directory or Settings.
- **Hidden on the project page**: the owner's name, the "Tasks" card (family to-dos linked to the project, which name family members), the Settings form except Documents, and the share switch.
- **Emails**: none besides the sign-in code. A weekly project summary for guests could come later; it needs `hub-jobs` and a consent step.

## 7. Decisions for the owner

1. **Role**: guest is a non-member with own tables and policies, as above. Agree?
2. **Gantt private notes** (task notes kept off the share link): guest **sees and edits** them (recommended; they're working notes). Alternative: hide them, which needs a server-side merge so a guest's save can't erase them (about a day more).
3. **The project's family Tasks card** (to-do rows that name family members): **hidden** from guests (recommended), or shown without names.
4. **Contractors**: guest sees name, company, trade, phone, email, website for contractors on their projects and can add new ones (recommended). Or read-only, no adding.
5. **Share link**: guest can copy it but only parents turn it on or off (recommended), or guest controls it too.
6. **Documents link**: Drive addresses only, family and guest only, **not** on the public share link (recommended).
7. **Assigning**: per project, in the project's Settings, plus a Guests list in Settings (recommended).
8. **Guest landing**: straight to their project when there's one; no emails besides the sign-in code (recommended).
9. **Hub file storage**: not recommended. Drive already gives versions, previews and per-person sharing, and hub storage would add a new access surface in a public repo for no gain.

## 8. Deploy order (once built)

1. Merge the site (it reads `hub_schema_version()`; guest pages need 11, so nothing changes until step 2). No Edge Function or `cron.sql` change.
2. Paste 0011 in the SQL Editor (refuses without 0010, or twice).
3. A parent adds the guest on the project; the guest signs in with a code.
