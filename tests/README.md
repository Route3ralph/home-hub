# Tests

Run everything from the repository root:

```sh
tests/run.sh            # all suites, then the totals; exit status 0 only if everything passed (about 13 minutes)
tests/run.sh fn e2e     # only the suites named (db, contract, fn, e2e, realdb, docs)
```

Each suite also runs on its own:

```sh
bash tests/db/run.sh
bash tests/contract/check.sh                     # or: bash tests/contract/check.sh assets/modules/today.js
node --experimental-strip-types tests/fn/send-email.test.ts
node tests/e2e/v1.test.js
bash tests/realdb/run.sh                         # or: bash tests/realdb/run.sh flows   (one file)
node tests/docs/docs.test.js
```

## What you need

- **Node 22 or later** (the Edge Function tests use Node's built-in TypeScript type stripping).
- **Playwright with Chromium** for the browser tests: `require('playwright')` must work (`npm install -g playwright && npx playwright install chromium`).
- **PostgreSQL 16** binaries for the database tests, the contract check, `fn/cron-sql.test.ts` and the real-database tests (see `tests/db/`).
- **git history** back to commit `b980d4c` (the v1 site) and `bcf296a` (PR A) for the real-database tests' v1-on-v2 checks; in a clone without them those checks print `SKIP` and are left out.

No network access is needed. The browser tests never reach Supabase or a CDN.

## The suites

| Folder | What it checks | How |
|---|---|---|

| `contract/` | Every database call in the site and the Edge Functions (`sb.rpc`, `core.v2.call`, `.from`) names a function or table that exists, with argument names it takes, and that the caller (signed out, signed in, Edge Function) may use | `tests/contract/check.sh` builds the same throwaway Postgres (`tests/db/cluster.sh`), reads its catalog and runs `check.js` over the code |
| `fn/` | Edge Function handlers (`supabase/functions/*/handler.ts`), hub-jobs' Google Calendar job (`calendar.test.ts`: signing in, reading, writing and Test, against a fake Google) and `supabase/cron.sql` | `tests/fn/*.test.ts`, in Node with type stripping; Resend, Google, the database and the clock are injected fakes (`cron-sql.test.ts` runs cron.sql in a throwaway Postgres) |
| `e2e/` | The site in Chromium: sign-in, every page, the share page, My day, phone layouts | `tests/e2e/*.test.js`: Playwright against `mock.js`, an in-browser stand-in for Supabase |
| `realdb/` | The family's key flows in Chromium against the **real** database: schema, migrations, RLS, every function, the real hub-jobs handler; and the v1 sites on the v2 database | `tests/realdb/run.sh`: a throwaway Postgres behind `server.js`, a stand-in for PostgREST and Supabase Auth (about 2.5 minutes) |
| `docs/` | `CLAUDE.md`, `README.md`, `docs/v2-design.md` and this file say what the code does; no file carries a word of a medical or learning label | `tests/docs/*.test.js`: reads the files only |

## Database tests (`db/`)

- `cluster.sh` starts the throwaway Postgres. Its databases are UTF8 with the C locale, as on Supabase: in a SQL_ASCII database the text cleaning in migration 0003 can't see the characters it removes.
- `run.sh` loads the fixtures and runs every `*.test.sql`. Besides the tests themselves it checks the migrations: 0002, 0003, 0004 and 0005 each refuse to run twice; 0003 refuses a database without 0002, 0004 one without 0002 or without 0003 (`hub_02_again`, a copy of `hub_02`), and 0005 one without 0002, at 0002, or at 0003 (`hub_03_again`), each changing nothing; and 0004 run again on a database whose `hub_schema_version()` was set back to 3 says "set back to 3", and 0005 on one set back to 4 (`hub_set_back_4`) says "set back to 4", each changing nothing (0005's check compares every function in `public` and `private`, body and all). `preflight.sql`'s promise about 0002 is checked against `hub_02` (the v1 database plus 0002 only). Two checks hold the replaced functions to their old output:
  - the **same-output check** (step 5b, `same_output.sql`) gives `hub_02` and a copy with every later migration the same household and compares `digest_for`, `day_text` and `get_person_day` for every person over the 14 days around Nov 1, with no calendars, no meals and no list, so the six functions 0003 replaces, and 0004's `get_person_day`, `day_text` and `digest_for` wrapper, still say exactly what 0002 said;
  - the **same-wall check** (step 5c) loads `calendar_fixtures.sql` into `hub_03` (migrations up to 0003) and a copy of it that gets 0004 and later, and compares `private.calendar_desired`, `calendar_plan` and `calendar_preview` for every calendar, column by column with nothing stripped, at three times (Oct 27, and 07:00 and 23:30 on Nov 1), with no meal planned: so wrapping `calendar_desired` and replacing `calendar_plan` changed no event on the wall. Then a dinner added to the copy must give exactly one more desired row, of kind `'meal'`, on the Family calendar. A later change to a wrapped function's `_v3` body needs its own such check (`docs/v2-design.md` §9).
  - the **homework-off check** (step 5d) builds `hub_04` (migrations up to 0004) and a copy that gets 0005 and then homework rows for a kid whose homework is off (homework time, a tutor link, an assignment with two steps, a block, points, a reward and an ask, the AI switch and its words), and compares `digest_for`, `day_text` and `get_person_day` (`same_output.sql`) on both: so replacing `get_person_day` changed nothing while homework is off. Then homework turned on for Taylor must add only her `homework` card to her own My day, and nothing to anyone else's or to her texts.
- `calendar.test.sql` covers Google Calendar (migration 0003): routing, descriptions, ids, daylight saving, the plan and what is recorded, storing a read and putting back changes made in Google, `google_items`, who sees which Google events, the parents' email, the job's lease and pause, and the role matrix; and meals on the wall (migration 0004): one all-day event per meal on Hub – Family, locked meals, the switch, and the plan keeping past dinners as history. It has its own household (`calendar_fixtures.sql`), with writing calendars for Alex, Jordan and Taylor, Pets ("Dogs"), House and Family, and a read-only Family calendar.
- `homework.test.sql` covers Homework (migration 0005, `docs/v1.3-homework.md`): turning it on and homework time (`add_homework_time`: ISO weekdays, the first day, days off, the event and its link); free minutes (`private.free_minutes`: a one-day change, a cancelled day, a day off, his timed events and tasks plus 15 minutes after one, all-day events, a Google event, other assignments' steps, the 2026-11-01 clock change, the 56-day cut); placement (`private.place_steps`: in order, between fixed steps, no room, the turn-in on the due date, the horizon); plans (the limits, starter plans, the kid's rules, Re-plan, saves on an old copy, giving); steps (ticks, Undo within 15 minutes, Not today, Make it smaller, questions and answers, checks, Not yet, taking a check back); focus blocks and points (one open block, his own block, the on-time window, seen minutes, the daily and weekly caps, a block crossing midnight, resends that earn nothing more, points off); rewards and trades (asks, held points, Yes and Not now, suggestions, given and voided points); his own homework, Quick and his preferences; his view and the card on `get_person_day`; the tutor link (what it shows and never shows, `last_used_at`, its writes, a moved due date, the daily cap, off, replaced, expired, homework off, an inactive kid); the AI's SQL side (the never-send words, the preview, `homework_ai_start`'s order of refusals and caps, the lease and the sweep, two sessions starting at once through `dblink`, `homework_ai_finish` with good and bad drafts, `private.scrub`); retention and Erase; and every role (Sam reads and every write refuses him; a stranger, a removed member and anon get nothing). Its household is `fixtures.sql`'s, where Taylor is the kid, with its own rows; `hub.now` moves per case.
- `food.test.sql` covers Food (migration 0004, `docs/v1.2-kitchen.md`): meals (who can do what, the checks, cleaning and stamps, the column grants); the shopping list for members (amounts such as "2 lb ground beef", aisles, "Leche" and "Milk", the lock, ticking against the state the phone saw, Undo, the 200-line cap, `shopping_list()`, renames and Forget, two sessions adding at once); the list on My day (who gets it, `helper_list`, the lock, Undo, the daily caps in `my_day_use`, midnight, `suggest`); and meals in `get_person_day`, `day_text` and the morning email (the `digest_for` wrapper equals `private.digest_for_v3` while no meal is planned). `food_other`, a lookup in `private.food_pairs`, must answer exactly as its old per-call version (kept in the file) for every `food_words` word in both languages and several spellings, and `shopping_list()` and `get_list_by_token` must each answer in under 250 ms at the 200-line cap. Every change sent with a key (`private.list_done`) is done once: a second try gets the first answer and changes nothing (a resent add never brings back a line bought in between), with the `seen` the change gave the line, not the one someone else gave it since; and a key is its sender's and that change's (a tick's line and direction, whatever its `seen`). `access.test.sql` checks that `food_pairs` and `list_done` are the only tables in `private`, each with RLS, no policies and no privilege for anon, authenticated or service_role. Its household is `fixtures.sql`'s, where Morgan is the Spanish-speaking helper and Taylor a kid; `hub.now` moves per case, through midnight and the Nov 1 clock change.

Every test file prints one line per check, `PASS  name` or `FAIL  name  (detail)`, and exits non-zero if anything failed. `run.sh` adds up those lines. A file that crashes, or exits non-zero without a `FAIL` line, also fails the run. (A `SKIP  …` line is a note, not counted.) New test files only need to follow the same pattern and be named `*.test.ts` (fn) or `*.test.js` (e2e, realdb, docs).

## Browser tests (`e2e/`)

- `server.js` serves the repository on a free local port; each test file starts and stops its own.
- `mock.js` answers everything the site asks of Supabase: Auth (sign-in codes), tables (`/rest/v1/<table>` with the usual filters, ordering and row-level security for members only), RPCs and Edge Functions. `makeDb()` returns a fresh fictional household: two members, two contractors and three projects (the kitchen schedule comes from `supabase/kitchen-renovation.json`). Add tables by adding arrays to the object it returns.
- `vendor/supabase.js` is supabase-js 2.117.3 (the version `index.html` loads from jsDelivr), served in place of the CDN copy. Its licence is in `vendor/supabase-js-LICENSE`.
- `withCalendars(db, sync)` adds the four Google Calendar tables (`calendars`, `calendar_links`, `google_events`, `calendar_sync`; `sync` sets fields of the one `calendar_sync` row) to a database. The mock applies their row-level security, column grants, checks and trigger, has fakes for `google_items` and `calendar_preview` (`calendarRpc`), and answers hub-jobs' `calendar` and `calendar_test`. Use it only for a schema-3 database: `makeDb()` leaves the tables out, so on schema 2 a stray request fails as it would in production. `calendarRow`, `linkRow` and `googleEventRow` make rows.
- `withFood(db, opts)` adds schema 4's food tables (`meals`, `shopping_items`, and `my_day_use` for My day's caps) and the household's `meals_on_wall` and `helper_list` (migration 0004, `docs/v1.2-kitchen.md` §3–§4), and 0003's calendar tables (`withCalendars`) when the database doesn't have them yet, as a schema-4 database does. The mock applies their row-level security, column grants, checks and tidy triggers, and `foodRpc` fakes the list functions with the migration's rules and shapes (`shopping_list`, `add_to_list`, `buy_item`, and the token functions `get_list_by_token`, `add_to_list_by_token`, `buy_item_by_token`, which a My day test routes itself, as `day.test.js` does the others). On a database without `withFood` they answer 404, as live on schema 3. `personDayFood(db, person, answer)` adds `get_person_day`'s `meals` and `list` keys; `mealRow` and `shopItem` make rows. "Now" is `db.foodNow` (ms; from `db.clock`'s household date and time, or `opts.now`), and every write is stamped with microseconds, as Postgres keeps them.
- Homework (schema 5, migration 0005, `docs/v1.3-homework.md` §3) has two sets of fakes, for its two sides. `withHomework(db, opts)` adds the eleven homework tables, the household's three AI columns, `events` and `event_changes` when missing, and schema 4's tables (`withFood`) when the database doesn't have them yet; the mock applies their row-level security, column grants, checks and tidy triggers, and `homeworkRpc` fakes the signed-in functions the Homework page calls (`homework_week`, `save_homework_kid`, `add_homework_time`, `save_homework_plan`, `homework_step`, `decide_reward`, `give_points`, `void_points`, `save_tutor_link`, `new_tutor_token`, `erase_homework`), placing steps with `assets/plan.js`'s own rules (`homePlan()` loads it in a vm), so the fakes and the page agree. Use it only for a schema-5 database: on 4 and below a stray read answers 404, as live. `withHomeworkTokens(db, { now })` and `homeworkTokenRpc` are the token side: Jordan's seven functions and the tutor link's four, with the migration's rules, messages and shapes (free minutes from `db.hwTimes` and `db.hwBusy`, placement, points and their caps, the daily caps on writes; `db.hwNow` is the server's clock), which a test routes itself, as `day.test.js` does the other token functions; `personDayHomework(db, person, answer)` adds `get_person_day`'s `homework` card. `day.test.js` uses them for Jordan's homework on My day (the card and its one-tap Start, `#homework`, `#focus` counted from the server's clock with the phone's a day off, the stuck sheet, the end screen, `#points`, `#plan/<id>`, every new word in Spanish), and `tutor.test.js` for the tutor link. `hwKidRow`, `tutorLinkRow`, `assignmentRow`, `stepRow`, `sessionRow`, `rewardRow`, `askRow` and `ledgerRow` make rows for the Homework page's tests; `tkKidRow` to `tkLedgerRow` the same for the token side.
- `install(page, db, log, opts)` options: `noConfig`, `emailSending`, `smtpDown`, `offline`, `fnStatus` / `fnBody` (Edge Function reply), and `rpc: { name: (db, body, email) => result }` for database functions. An RPC without a handler answers 404 "Could not find the function", like PostgREST. That is how the v1 tests run: there is no `hub_schema_version`, so the site is in v1 mode. Pass `rpc: { hub_schema_version: () => 2 }` for v2 mode.
- `signIn(context, email)` starts a browser context already signed in.
- Screenshots go to `e2e/shots/`, which git ignores. Look at them after changing a page, on desktop and phone sizes.
- In v2 mode the core loads the people, the household and the clock at sign-in, so a v2 test needs `db.people` and `db.household` arrays and RPC fakes for `clock` (`{ local_date, local_time, tz }`) and `mark_signed_in` (`null`). Fakes should answer with exactly the shapes in `supabase/migrations/0002_home_hub_v2.sql`.
- Saving a project schedule sends `task_dates_at` from the device clock. A test that saves a schedule twice should let the clock move (`page.clock.install` then `resume`) rather than fix it, or the two saves carry the same timestamp.
- `modules.test.js` checks the module system (script order, which tabs show for each schema version, `ctx.signal`). It adds throwaway "probe" modules by appending them to the last module script in the browser, so nothing test-only ships in the site.

## Real-database tests (`realdb/`)

The browser tests in `e2e/` answer the site from JavaScript fakes of each database function. This suite runs the same kind of flows against the real SQL, so a fake that drifts from the migration (a renamed parameter, a different shape, a policy that refuses) shows up here.

- `run.sh` starts a throwaway cluster (`tests/db/cluster.sh`) and builds four template databases: `realdb_t` (the Supabase stand-ins, `schema.sql`, a v1-era household from `seed_v1.sql`, `migrations/*.sql`, then `seed_v2.sql`), `realdb_v1t` (the v1 database as it was live before v2), `realdb_v2t` (the v2 database before v1.1: migration 0002 only, then `seed_v2.sql`) and `realdb_v3t` (the database before v1.2, as it is live while the new site goes out first: migrations 0002 and 0003, then `seed_v2.sql`). It exports the older sites into `tests/.tmp/` (`b980d4c`, the v1 site, under `/v1/`; `bcf296a`, PR A, under `/v1a/`) and runs every `tests/realdb/*.test.js`. Each file copies a template into its own database and starts its own server, so files share nothing.
- `server.js` serves the repository and answers `/rest/v1/…`, `/rest/v1/rpc/…` and `/auth/v1/…` the way PostgREST and Supabase Auth do: each request runs in its own transaction as `anon` or `authenticated`, with the JWT's claims in `request.jwt.claims`, so row-level security and grants apply for real. Filters are PostgREST's, logical ones too (`or=(…)`, `and=(…)`, nested, `not.or=`), which `access.test.js` checks against the SQL they stand for. The sign-in code is always `123456`; new emails go through `hook_family_only_signup`. `/functions/v1/hub-jobs` runs the real handler (`supabase/functions/hub-jobs/handler.ts`) with only Resend and Google faked. Test-only endpoints: `/__test/sql`, `/__test/clock`, `/__test/requests`, and `/__test/migrate` (a migration file run in a session of its own, as in the SQL editor, after which the server reads the schema again, as Supabase's PostgREST does after DDL).
- `lib.js` gives each file `setup(name)` (`setup(name, { v1: true })`, `{ v2: true }` or `{ v3: true }` for the older templates): `open({ email, phone, path })` for a signed-in (or signed-out) browser, `sql(…)` to look at what the database kept, `requests()` / `failed()` for what the site asked, `runDigest()` for the morning email, `runCalendar()` for the calendar job and `hubJobsAs(email, body)` for Sync now, Test and preview, `setClock(…)` to move the household's clock (it starts on Tue 2026-10-27 at 09:00 in New York; the browsers run in Los Angeles), and `migrate(file)` to apply a migration the way the owner does, in the middle of a test.
- **The fake Google** (`fakeGoogle` in `lib.js`, `h.google`): hub-jobs' `fetch` reaches it for `oauth2.googleapis.com` (it checks the signed request against the key pair `lib.js` makes for `GOOGLE_SA_JSON`) and `www.googleapis.com/calendar/v3` events, and it keeps what was written, calendar by calendar, the way Google does (a deleted event keeps its id, so a POST is 409 and a PUT brings it back; times come back in the calendar's zone). A test adds calendars (`add`), types events into Google (`typeIn`), edits or deletes them there (`edit`, `remove`), and reads what is there (`events`) and every call (`requests`, `writes`). The hub's clock doesn't move by itself, so a test moves it 15 minutes when the next run should read the calendars again.
- The files: `flows.test.js` (sign-in, Today, a weekly event, a monthly task, the starter list, the Directory, Family, Settings, Projects, My day, a member's view, the v1 sites), `jobs.test.js` (the morning and evening email runs, Settings' status and preview; then Google Calendar: Settings sets calendars, Tests, approves and Syncs now, what Google holds, a second run that writes nothing, an edit and a delete, events typed into Google on the Calendar page, `day_text`, the email and My day, and changes in Google put back), `access.test.js` (what anon and a non-member can reach, the Google Calendar tables and functions included, and Food: with a locked dinner, a locked line, a bought line and a `my_day_use` row in place, signed out only the token functions answer, a stranger gets no rows and empty lists, and a member reads everything but can't add a line, write `bought_at` or read `my_day_use`), `v1db.test.js` (the new site in v1 mode on the live v1 database), `v2db.test.js` (the new site and hub-jobs on the v2 database before migration 0003: no calendar request, Settings waiting for the database update, the calendar job answering 503 no_schema), `v3db.test.js` (the new site and My day on the database before migration 0004, `realdb_v3t`: no Food tab, no Shopping in the Add sheet, no `meals`, `shopping_items` or list request, nothing failing, and My day as before). With v1.2, `flows.test.js` also has two grown-ups on the Food page at once, Taylor's list on My day in Spanish (an add of "Leche" while "Milk" is to buy, ticks made offline that arrive once), Jordan's My day with dinner and no list, a dinner reaching Today and My day, and a locked dinner's prep reminder, which the real task form saves as a private task ("Private item" on the cook's My day, text and email subject); `jobs.test.js` sends a dinner to the fake Google's Hub – Family ("Dinner: Tacos (Sam)", all day; "Dinner: Private item" when locked) and into the email, and applies 0004 to a database where the calendar job has already run, then runs it again (a second setup in the same file, `jobs3`, on a copy of `realdb_v3t`; the file fails if either does). The Food flows in `flows.test.js` run in order and build on each other (the list Taylor sees counts the lines added before it), and `jobs.test.js`'s dinner flow runs last on its main database and leaves the clock on Oct 30.

## Docs check (`docs/`)

`docs.test.js` reads files only. It checks that deploy steps 4 and 5 (in `CLAUDE.md`, `docs/v2-design.md` §7 and the README) name every secret hub-jobs reads and both Vault secrets `cron.sql` needs; that `CLAUDE.md` and this file name every suite `run.sh` runs, and this file every browser and real-database test file; that `index.html` and `day.html` carry one `?v=`, and that `CLAUDE.md` names the scripts each loads, in order (and `day.html`'s stylesheets), and every way into `day.html` (`?t=`, `?c=`, and from v1.3 `?h=`, also in the design's §4); that `docs/v2-design.md` names every table, column and public function the migrations add, with the real parameter names in every signature it (or `docs/v1.1-google-calendar.md`, `docs/v1.2-kitchen.md` or `docs/v1.3-homework.md`) writes out; that anon can call exactly the nineteen token functions the design lists and counts (and `CLAUDE.md` names for `day.html`); that `docs/v1.2-kitchen.md` §2 and `docs/v1.3-homework.md` §2.1 count what 0004 and 0005 add (0005's tables by name), and the latter's §3.6 the token functions; and that, from migration 0004 on, the design (§9, §10) writes out each new table, added column and constraint exactly as the migration has it (in its `sql` code blocks, comments and spacing aside), the signature of every public function, every private function, and both names of every function a migration renames. When it fails, fix the doc (or the code), not the check.

`labels.test.js` holds the one list of words of a medical or learning label (`docs/v1.3-homework.md` §13.1 item 8) and checks that none of them is in any text file under `supabase/` (the migrations, and the AI planner's prompt once it is in `hub-jobs`), `assets/` or `tests/` (the fixtures and every test; `tests/docs/` itself is left out), or in the pages and the docs. It also checks that its matcher finds each word on the list and passes ordinary words ("executive-function support", "disabled", "diagnostic"), and that the scan reads the files that matter. A word on the list in a new file fails it: say it another way.

`tests/.tmp/` is git-ignored scratch space for any suite that needs it.

## Test data

Fixtures are fictional: people such as Alex, Sam and Jordan Example, numbers in the 555-0100 to 555-0199 range, and `example.com` or `.example` addresses. Never use a real person's name, number, address or account, or a real project ID. Never give anyone, real or made up, a medical or learning label (`labels.test.js` checks).
